# INTERNAL_DELIVERY：清楚可用的交付目录

## 1. 默认交付方式

工作区保留数据、实验、草稿、审核稿和历史版本；交付目录提供当前已经验收、可供队员使用的成果。完整项目开始组织工作区时就明确入口，有首份有效成果即创建相应支撑材料目录，比赛过程中动态维护。

默认 `delivery_root = workspace_root/交付文件夹`，用户指定外部目录或已有交付位置时沿用，不擅自搬迁。推荐结构：

```text
交付文件夹/
├─ 交付说明.md
├─ 交付清单.json
├─ 论文/
└─ 支撑材料/
   ├─ 01_结果表/
   ├─ 02_求解代码与输入/
   ├─ 03_补充实验/
   ├─ 04_验证记录/
   └─ 05_论文图表/
```

按实际内容创建，避免空目录、占位成果及双层同名“支撑材料”。论文目录只保留一个当前有效版本及约定的源稿；未形成整篇有效稿时，在说明中列出已有内容，不能放置冒充终稿的文件。

仅初始化、交单问成果、交源码或修一个文件时，只完成用户请求的范围。局部交付不能被报告为全题完成，已有队员终稿也不需要补造一套 AI 参考稿。

## 2. 交付责任与入口

三角色模式下，代码手交代码、输入、环境与运行入口；建模手交必要推导、核验与结论边界；论文手交论文及图表、附录清单；主 agent 回读并整合交付目录。单代理承担相同职责。

使用 [交付说明模板](../assets/DELIVERY_README_TEMPLATE.md)，说明文件用途、实际环境、外部输入、运行顺序、预期输出、验证范围及未完成项。只列实际使用的软件：不要求所有团队使用 SPSSPRO，也不为未使用的工具建目录或补截图。

每问的可交接内容应串起题意、选择理由、数学模型、实际运行/推导、结果与核验、限制和向后问接口。教程和说明不重复复制所有日志，而是引用权威来源。

按“计算、核验、论文材料、交付”分别报告状态。完成代码计算不等于完成论文表格或交付目录。正式结果发生变化后，更新受影响的论文、表图与清单，避免保留两个含义不明的“最终版”。

### 动态同步：成果变化即处理

`支撑材料/` 是持续更新的当前有效成果集。同步由主 agent 负责，单代理直接承担；不是赛末打包动作，也不能只等每问结束。

| 触发事件 | 当轮同步动作 |
|---|---|
| 新结果、代码、输入、模型说明、图表或验证记录形成 | 检查实际文件与依赖，核验后更新对应材料及运行入口；记录来源版本/Run、hash、用途与最近同步时间 |
| 上游输入、模型或结果变化 | 立即标明受影响材料与论文引用过期/待更新；不能继续标为当前有效，即使新版本尚在运行 |
| 新版本核验完成 | 将完整有效副本替换到对应位置，同步图表、附录文件名、交付说明和清单；替换完成后才将状态恢复为就绪 |
| 材料废弃、被替代或不再属于当前交付范围 | 旧版与原因保留工作区历史；核对依赖及队员改动后移出当前交付集，修订引用与清单 |
| 中断、交接或恢复会话 | 对账源版本与交付清单，先补齐待同步项；无法补齐时在入口列出受影响文件与缺口 |

“实时”指 agent 在处理上述变更的同一工作轮次完成对账与可完成的同步，进行中/核验未过的产物明确显示状态；不宣称会话结束后仍有后台监听。无需另建状态数据库或未经请求的定时任务。

只同步已经完整写入的有效文件，不复制正在写入的半成品；新旧文件全部对账后再更新清单，避免清单先显示完成。发现队员修改过交付副本，先保留并对账，不能被自动同步覆盖。状态、来源和未完成项沿用已有 README、交付说明及清单，不维护平行账本。每问结束和最终交付仍作一次整体核对。

## 3. 论文、代码与图表

论文工作稿可随解题推进；冻结交付论文时应基于 `PAPER_EVIDENCE_BLUEPRINT_READY`，检查模型、推导、Final/Validation Run、数字、比较条件、文献与结论一致。

- PDF 是便于阅读与验收的成品；源稿按团队约定使用 DOCX、LaTeX 或不交源稿。不能把 DOCX＋PDF 当成所有团队的固定组合。
- 队员须理解、核查、参与表达并确认论文；有人工摘要时保留有效表达。是否另需重写、披露或特定格式，由适用比赛规则决定。
- 论文图由 Python 随问生成并验证，遵循 [科研图适配规范](python-visualization-policy.md) 指向的 `Yuan1z0825/nature-skills` 的 `nature-figure`，不能拖到最后补画。交付绘图脚本、必要数据和图表清单；不在本规范重复规定尺寸、颜色或单图/多图布局。
- 每张正式图能追到脚本、数据与 Run/方法版本，并说明回答的问题、正文位置与支持的判断；AI 沟通图和安全审计图不混入论文图。
- 每张论文图表下方保留解释性图注/表注，说明展示内容、主要发现、支持的判断及必要边界；导出和精简不能只留下标题。
- 求解代码使用项目实际语言和工具，包含真正的入口、辅助模块、绘图/验证脚本及必要且允许分发的输入、配置和依赖说明。
- 不能分发的数据须提供获取方式、处理方法及其对复现的影响。总运行入口只运行已完成且获确认的模型链。

不以扩展名清理材料：Markdown、JSON、配置或运行记录可能是代码必读依赖。删除前检查实际依赖；保留应提交的引用、许可和 AI 使用信息。

## 4. 最终材料的隔离验收

先检查依赖，再冻结当前选定成果和清单。清单沿用 `files[{path, sha256, size}]`，相对路径以本次验收目录/ZIP 根为基准；清单不包含自身的递归 hash。由选定源文件生成可信对账清单，不能从收到的包反向生成清单后宣称版本正确。

1. 目录复制到新的隔离验收区；ZIP 真实解压。检查相对路径、链接、预算、数量、大小和关键文件。
2. 在隔离副本中打开和解析成果，检查论文公式、图表与实际渲染。正文、说明和图表链接须能从包内定位；不得将 Windows 盘符或 `file:` 链接误当网络地址而跳过。依赖原工作区绝对路径的图片/引用先映射为包内相对路径，再实际打开复核。
3. 按说明真实运行已授权的复现入口，只提供已声明的外部输入。输出写入验收区，不覆盖冻结的正式结果。
4. 分别说明“重新求解”和“重建已交付结果”：前者从模型和输入重新计算，后者回放或核对冻结结果。多解、随机性或平台差异须说明允许差异与判定标准。
5. 与当前 Final Run/推导和选定论文版本对账；核对论文附录文件名与实际交付清单。
6. 记录本次验收时间、环境、命令、输出与限制。没有实际重跑的部分标为未验证，历史 PASS 不代替本次最终包验收。

若用户只要求局部交付，验收仅覆盖该范围。完整交付要求的关键项失败时标记 `DELIVERY_INTEGRITY_FAILED`，修复后才能宣布对应范围完成。

## 5. 机械验收工具

```bash
python scripts/delivery_check.py 交付文件夹 --require 交付说明.md --manifest 交付文件夹/交付清单.json
python scripts/delivery_check.py 交付文件夹/论文 --profile reference-paper --paper-source latex
python scripts/delivery_check.py 参考论文.zip --profile reference-paper --paper-source docx
```

工具支持目录和 ZIP。`auto` 识别名为“参考论文”的目录或 ZIP；其他名称显式指定 profile。`reference-paper` 始终要求非空有效 PDF；`--paper-source docx|latex|none` 分别另需 DOCX、TEX 或不要求源稿，默认 `docx` 保持旧命令兼容。泛用支撑材料使用 `generic`，不强制附带论文。

目录在解析或哈希前检查条目数、总大小与链接；符号链接和 Windows junction/reparse point 均拒绝，须物化为允许分发的真实文件。ZIP 先检查路径、资源预算和 CRC，再真实解压走相同内容检查。

`--require` 可重复声明必需的相对路径，包括 Markdown 运行依赖。PDF 解析依赖 `pypdf`，依赖缺失明确失败。空 `__init__.py` 可保留，其他空成果不能冒充完成。

输出 `MECHANICAL_ONLY`：工具检查 Python 语法但不执行代码；TEX 只检查存在且非空，不调用编译器。工具不会证明数学正确、真实复现、XLSX 内容正确或图表可见。PDF 有绘制指令仍可能因透明、白色或裁切不可见，必须另行渲染 QA。

## 6. 四包按需导出与官方提交

用户需要分类归档或传输时，可从已验收目录筛选：`题目详解.zip`、`参考论文.zip`、`源码.zip`、`其他.zip`。只请求其中一包就验收这一包，不强制四包齐全。原工作区和已验收材料保留，打包失败不损坏原成果。

四包用于理解、复核和留档，不自动等于官方上传材料。官方导出遵循 [官方提交规范](official-submission-policy.md)，按实际格式、大小、页数、匿名和 AI 使用要求筛选。不能把某队的 30 页或 20 MB 固化为通用要求。

对完整请求，只有约定文件、论文与关键复现验收均完成，才标记 `INTERNAL_DELIVERY_COMPLETE`；局部完成明确列出范围与剩余项。
