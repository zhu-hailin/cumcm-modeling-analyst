# 摘要与论文论证协作

## 1. 目标和使用时机

写作、摘要审改或论文快读时加载。摘要帮助读者理解做了什么、为什么这样做、结果意味着什么，而不只是展示模型名称和数字。

读题后建立全文主线，每问完成后积累素材，最终按冻结证据统一。单代理承担相同职责；三角色中论文手组织表达，建模手提供选择理由和解释，代码手提供真实结果与比较口径，主 agent 核对证据及版本。

队员应理解、核查、参与表达并确认；不默认要求把协作成果全部人工重写。已有人工摘要先识别有效结构、措辞和判断，再做局部补强。适用规则另有要求时按规则处理。

## 2. 从证据组织为摘要

采用以下组织原则，不要求各问使用同一句式或固定篇幅：

```text
实际困难 → 针对性建模 → 关键结果与对照
→ 结果解释 → 最终判断及成立条件
```

执行顺序：

1. 从各问已验证成果提取困难、设计、结果、解释、取舍及证据引用。
2. 确定全文共同主线及各问递进；本来独立的子题不虚构依赖。
3. 选择能支撑判断的数字，交代比较对象、单位和适用范围；省去无助于理解的程序字段、变量总数和求解器细节。
4. 保留人工稿的有效表达，补足缺失的机制、比较条件和结果含义。
5. 回查蓝图与 Final/Validation Run，确保摘要、正文、表图和结论属于同一有效版本。
6. 独立快读：只看摘要能否说清做了什么、为何这样做、发现什么、最终如何选择。

没有真实创新证据就不硬写创新句。数值变好不自动等于方案全面更好；未跑实验、未检验显著性和未证明最优性不能靠措辞补齐。

## 3. 指标权衡的合成示例

以下仅示范表达逻辑，数值为合成示例，不能用于真实赛题或运行结果：

> 为降低运行费用，在基准调度中加入预测更新机制。同一组场景下费用降低 8%，但应急需求增加 12%，说明成本收益伴随额外风险。因此仅在应急资源充足的场景采用更新策略，其余场景保留基准方案；该选择的适用范围仍限于已测试场景。

该段将困难、设计、比较、解释和判断连接起来。若尚未检验应急资源是否充足，最后一句应写成待验证条件，不能包装成已经完成的可行性结论。具体论文可采用不同写法，不照抄此句式或数字。

## 4. 正文论证与精简

论文的可审阅思考过程体现为模型选择依据、必要推导、真实实验及解释，不要求记录全部内部推理、聊天和调试轨迹。

- 公式前交代要解决的困难和引入理由，公式后解释含义、量纲、参数来源及关键变换。
- 明确数学模型、求解算法、求解器与经验策略的作用；工具品牌与复杂度不是论证。
- 结果按照观察、比较、解释、回答原题和适用边界组织，避免逐格念表。
- 有价值的否决方案可用于解释取舍；事后认识如实标注，不编造成事前实验设计。
- 精简先删重复，保护动机、方法归属、比较条件和结论边界；删段移表前核对题面及 `required_location`。
- 图表在比赛过程中随问使用 Python 生成，统一通过 `python-visualization-policy.md` 使用 nature-skills；不能把图表解释和生成一起拖到最后。

已有可靠答案时，追加实验应能改变模型、结论、证据强度或决策。临近截止，优先补足论证、摘要和交付缺口，同时保留关键约束与决定性验证。

## 5. 独立快读与修订产物

审阅者先形成自己的阅读结果，再查看作者解释或其他代理评价。逐项记录“已清楚 / 需补强 / 无法核验”，不要设虚构官方权重或平均多个代理分数来预测奖项。

| 检查 | 可回答的问题 |
|---|---|
| 问题与主线 | 真正困难是什么，各问为何这样组织？ |
| 方法与理由 | 模型针对什么结构，为什么采用它？ |
| 结果与证据 | 哪些数字支持判断，比较条件是否公平？ |
| 解释与取舍 | 结果意味着什么，收益和代价是什么？ |
| 范围与真实性 | 结论在哪些条件下成立，是否超过证据？ |
| 表达与衔接 | 读者能否顺畅跟上推导、验证及跨问接口？ |

修订记录只需包含原位置、问题、证据位置与建议修改，不另建分数台账。技术核验失败与表达不清分别报告，前者须修复证据或结论，后者须改进组织与解释。
