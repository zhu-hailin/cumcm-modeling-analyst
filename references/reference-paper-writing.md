# AI 内部参考论文写作规范

## 1. 边界

AI 参考论文是基于冻结的 Final/Validation Run、`02_analysis/PAPER_EVIDENCE_BLUEPRINT.md`、真实图表/可编辑表格和已核验文献写成的队内参考稿。

它不是网上论文合集，也不是可直接提交的参赛终稿。队员必须理解、核查并人工重写。

默认：

```text
02_analysis/PAPER_EVIDENCE_BLUEPRINT.md   # 唯一权威蓝图
05_paper/
├─ outline.md
├─ draft.docx
└─ 参考论文.pdf
```

`final.docx/final.pdf` 只用于队员已经人工重写并确认的版本。

字号、页数、匿名、文件命名和提交格式以当年官方规则/模板为最高优先级。

Word 与 LaTeX 均可用于专业排版，按团队熟练度、协作需求和官方交付要求选择。格式验收看公式、字体、层级、图表和跨页一致性，不给软件工具排优劣；不为换工具而增加赛时迁移风险。

---

## 2. 完整参考论文的前置条件

只有以下条件满足后才开始完整写作：

- 题意与 Requirement Traceability 清楚；
- 每问 Final Run 已冻结，必要 Validation Run 已完成；
- `SCIENTIFIC_VALIDITY` 与 `CONTEST_TASK_COMPLETION` 已内部判断；
- 数据处理、模型前提、baseline/参照、验证和现实约束已审计；
- `PAPER_EVIDENCE_BLUEPRINT_READY`；
- 正式图表通过科研绘图 QA；
- 关键文献、外部数据、参数和来源已经核验；
- 重大跨成果冲突已解决。

缺少真实运行或可靠数据时，蓝图对应项保留 `BLOCKED` 或 `NOT_IDENTIFIABLE`，不能靠文笔补出完整答案。
已有验证充分的章节可以随题写入阶段稿，明显标出未完成部分；整体证据就绪后再统一摘要、图号和跨问叙述，不把全部写作拖到最后。

论文作者只从蓝图登记的 Final/Validation 成果读取核心数字，不从聊天、旧截图或旧 Run 手抄。

---

## 3. 总原则：问题驱动，不写成 Agent 日志

论文的核心评价逻辑可以概括为：

```text
题意理解是否准确
→ 假设是否必要、合理且真正被使用
→ 模型是否针对实际问题
→ 求解是否正确、可复现
→ 结果是否可信并满足现实约束
→ 表述是否清楚、连贯、自明
```

复杂模型名不是创新。创新只写真实实现并解决了实际困难的设计。

内部项目可以使用 `FINAL_RUN_ID`、A/B/C 证据等级、PASS/FAIL 等状态；**正式论文正文不机械展示内部 Agent 状态。** 正文用实际验证、误差、稳定性、适用范围和限制来表达证据强度。

每问开头优先让评委看到：

```text
直接答案 / 关键发现
→ 关键数字或规则
→ 方法概要
→ 最重要验证
→ 适用条件与限制
```

随后完整解释“为什么、怎么做、为什么可信”，避免写成简答题。

---

## 4. 摘要

摘要不是模型名称清单，也不是正文目录压缩版。应让评委不翻正文也能知道每问：

1. 解决了什么核心困难；
2. 采用什么关键思路/模型，为什么适合；
3. 如何求解或验证；
4. 得到什么直接答案与关键定量结果；
5. 主要可靠性证据和成立条件；
6. 有真实贡献时，再指出特色或创新。

“效果良好”“模型可靠”等空话用真实误差、准确率、区间、稳定率、目标函数变化、约束违反量等替代。

摘要中的数字必须能追到蓝图和 Final/Validation Run。原则上不放复杂公式、图表、参考文献序号和无法自明的内部符号。

摘要最后写或按最终结果重写。快读验收时，逐问检查“核心困难 → 关键模型及适用理由 → 定量答案 → 最重要验证/条件”能否被直接找到；篇幅不足优先保留直接答案和可靠性证据。没有创新证据时不硬加创新句，不能把尚未完成的实验写成摘要结果。

---

## 5. 问题重述与问题分析

### 问题重述

不是复制题面，而是明确：

- 实际背景；
- 已知条件与数据口径；
- 目标、对象、约束和交付项；
- 单位、范围和必要边界；
- 对题面歧义的合理澄清。

没有新增信息价值的同义长段落可以删。

### 问题分析

问题分析回答“为什么这样解决”，重点说明：

- 关键困难和数据结构；
- 因素/变量之间的逻辑关系；
- 为什么从当前机制或数学结构切入；
- 当前路线相对明显替代方法的适用性；
- 前后问题如何递进、复用和传递结果。

不要只写“问题一用 XX，问题二用 YY”。

---

## 6. 模型假设：每条都要有用途

每条关键假设至少回答：

```text
为什么需要？
依据或合理性是什么？
它在哪个模型 / 公式 / 约束中真正使用？
它可能怎样影响结果或适用范围？
```

不被后文使用的假设删除。

仅为了方便求解但可能显著影响结论的强假设，必须说明影响；必要时进入敏感性、情景分析或稳健性检验。

不要罗列“空气阻力忽略、对象均匀”等与当前模型无关的模板化假设。

---

## 7. 符号、公式与量纲

符号宜少而清楚。同一符号不得跨章节改变含义。

关键公式出现前先解释为什么需要它，出现后说明：

- 变量含义；
- 单位/量纲；
- 参数来源；
- 数学或现实含义；
- 对应代码模块/算法步骤。

禁止为了“看起来数学”增加代码中根本没有使用的装饰公式。

目标函数、关键约束、变换与逆变换必须与代码一致。

---

## 8. 每问章节：建模逻辑优先

章节可按实际题型组织，不要求机械套固定标题。典型论证链：

```text
直接答案与本问目标
→ 数据与结构
→ 为什么选择当前模型
→ 模型建立：变量、公式、约束、参数
→ 如何求解
→ 主要结果
→ 为什么可信：验证 / 敏感性 / 现实约束
→ 局限与向后问接口
```

### 8.1 为什么选这个模型

在公式之前说明：

- 当前问题真正难点是什么；
- 模型利用了什么数据结构、机制或约束；
- 为什么比明显替代方法更适用；
- 复杂度是否带来真实收益。

路线明显时不用为了“比较充分”强行罗列多个模型。

### 8.2 如何求解

不能只写“使用 Python/MATLAB 求解得到结果”。

对于数值优化、启发式、仿真或机器学习，解释足以复现结论的：

- 算法/求解方法；
- 关键参数或停止条件；
- seed / 重复机制（适用时）；
- 可行性修复、数值稳定或验证设置；
- 为什么这种求解方式适合当前模型。

软件只是工具，不是论证。

区分模型与算法：模型表达现实关系、目标和约束，算法负责估计或求解。同一模型换求解器应写为求解改进，不能冒充多个独立模型。比较路线时交代统一评价口径及选优取舍，不把全部探索过程写进正文。

### 8.3 结果分析

优先按：

```text
观察
→ 比较
→ 解释
→ 回答原题
→ 限制 / 适用条件
```

结果不能停在“如图表所示”，必须解释数值和现实含义。

禁止：

- 逐格念表；
- 把不显著写成完全独立；
- 把相关写成因果；
- 把启发式当前最好解写成已证明全局最优；
- 把聚类簇编号直接命名为确定阶段；
- 用最好 seed 或最有利场景冒充稳定性/普遍优势。优化题最终方案可以选最好已验证可行解，并交代选择规则和相应证据。

### 8.4 验证、敏感性与可靠性

验证强度与结论风险匹配，不机械要求每问做同一种敏感性分析。

可根据题型选择：

- 残差/误差分析；
- 滚动、分组、留出或外推验证；
- 独立算法或不同原理验证；
- 小规模精确解 / 上下界；
- 现实数据对照；
- 参数扰动、情景分析和决策翻转率；
- 多 seed / bootstrap。

核心不是“做了多少实验”，而是“结果为什么可信”。

灵敏度分析至少解释“为什么选这些参数/范围、结果变化多大、关键结论何时翻转、现实决策如何应对”。参数响应图与调参曲线、随机波动图区分；有上游不确定性且会改变后问决策时，说明传播及影响。详细实验设计见 modeling-research-playbook.md 第 11 节。

### 8.5 创新与小改进的表达

仅对实际完成且有依据的改进组织：原方法不足 → 本题具体改动 → 有效机制 → 对比/消融结果 → 代价与边界。
突出一个解决真实难点的改进即可；不以模型名新、堆叠算法或排版美观代替创新证据。无明显提升时如实写取舍，不写“显著优越”“首次提出”等无支持表述。

### 8.6 关键结果集中呈现

每问结果段优先给一份紧凑主结果表或清楚的数值句，包含对象、数值、单位和必要条件；精确方案/名单用可编辑表，趋势和结构用图，不强制两者都做。
主答案不只留在日志或长附录中；加粗只强调少量关键发现并服从模板，不整段加粗，不重复堆同一组数字。

---

## 9. 数据处理必须可见

不能只写“完成数据清洗”。关键口径至少说明：

- 样本/决策单位与数量；
- 原始、有效、排除数量（适用时）；
- 缺失、异常、零值、重复和单位处理；
- 处理规则及题意/统计依据；
- 插值、估计、仿真与真实观测的区别；
- 处理对结论可能造成的影响；
- 最终建模数据版本。

长表可以放附录，但影响结论的处理规则必须在正文可见。

---

## 10. 图表与总体技术路线

只使用已经升级为正式证据的图，不把 Stage 1 临时探索图直接放论文。

数据图证据链：

```text
结论 ↔ 图/表 ↔ 源数据 ↔ Final/Validation Run ↔ 代码
```

方法图证据链：

```text
Requirement ↔ 最终模型/假设 ↔ 代码/算法步骤 ↔ 绘图脚本 ↔ 方法版本
```

正式论文图默认采用**单图单文件、单图单图号**：

- 每个主要图表由 Python 单独生成一个独立图片文件；
- 正文和图题默认按 `图1、图2、图3……` 编号；
- 两张图即使在版面上并排，也优先保持两个独立图片文件和两个图号；
- 不为了省文件、省版面或营造“高级感”把独立图硬拼成 `(a)(b)(c)(d)`；
- 正文优先写“如图3所示”，不默认写“a图”“b图”。

只有当多个视角必须同时观察、共享同一坐标/尺度/图例，或拆开会明显破坏科学比较逻辑时，才允许少量组合面板图。此时整张组合图仍只有一个正式图号，例如 `图3`；`(a)(b)` 只用于必要的子图定位，正文仍优先引用整张 `图3`，只有讨论特定子图时才写 `图3(a)`。

需要总体路线图时，用一张紧凑学术图展示输入、关键预处理、各问核心方法、验证分支、跨问接口和最终输出。禁止仪表盘、KPI 卡片、App UI、发光、渐变、海报化大标题和内部 PASS/FAIL 状态墙。

图与表高度重复时保留更能支持判断的一种。大矩阵和长名单采用“正文摘要 + 附录完整可编辑表”。

---

## 11. 后台成果选编

按蓝图：

- `PAPER_CORE`：直接回答原题或最关键证据，进入正文；
- `PAPER_SUPPORT`：正文概述，详细稳健性/参数/长名单进入附录；
- `RUN_ONLY`：调试、否决候选、重复运行，不进入正文。

不要让论文变成项目目录转储，也不要因为“简洁”把直接答案和关键证据藏在后台文件里。

---

## 12. 文献与外部数据

严格区分题面数据、真实外部观测、插值/外推/估计、假设/仿真和学术文献。

- 不编作者、题名、年份、DOI、URL 或访问状态；
- 引用已有思想、模型、算法、数据或经验公式时，在实际使用位置标注；
- 参考论文只借鉴研究设计和证据组织，当前题参数、阈值、结果和图表重新运行；
- “文献真实且支持当前主张”与“存在公开可下载全文链接”分开判断，遵循 `source-verification-policy.md`。

---

## 13. 全文连贯性

论文不是多个独立问答的拼接。每问都应该接上整体主线：

```text
为什么这样做
→ 怎么做
→ 得到什么
→ 为什么可信
→ 对下一步有什么作用
```

重点检查：

1. 摘要；
2. 总体路线图（需要时）；
3. 每问首段；
4. 主结果表与图题；
5. 结论。

只看这些位置，应能复述每问的直接答案、核心模型、关键结果、主要不确定性和跨问接口。

问间过渡交代“前问产物是什么、为什么成为本问输入、本问新增了什么”。题目本来独立时说明共同背景或不同目标即可，不虚构依赖关系。

---

## 14. 结论

结论围绕原题交付项归纳：

- 每问最终答案和关键数字/规则；
- 最重要的模型机制或决策依据；
- 主要验证和可靠性边界；
- 前后问形成的整体认识；
- 仍存在的关键限制和真正可行的改进方向。

不要新增正文从未验证的新结论。

---

## 15. 生成与验收

生成 DOCX/PDF 后检查：

- 文件存在、非 0 字节、可打开；
- 每个 Requirement 有可定位主答案；
- 关键假设有必要性、依据、实际用途和影响；
- 模型选择有针对性解释；
- 求解不以“软件计算”代替方法；
- 关键结果有解释、验证和现实约束证据；
- 各问跨接口真实连贯；
- 正式图默认单图单文件，正文使用 `图1、图2、图3……` 的独立图号；例外组合图有明确必要性；
- 图表在最终 A4 尺寸可读且与 Final/Validation Run 一致；
- 公式、单位和中文字体正常；
- 摘要、正文、图表和结论没有串 Run；
- 引用真实且与正文用途对应；
- AI 沟通图、安全审计图、内部提示和 Agent 状态未混入正文；
- 快速阅读链能复述整题核心结论；
- `final-consistency-sweep.md` 通过。

失败应修复或明确说明，不能为了交付伪造完成状态。
