# Word / PDF / Markdown 公式渲染与验收规范

## 目标

数学建模中的公式、符号和变量必须既**写得正确**，也**解释得清楚**。

本规范同时约束：

- Markdown 教程与研究记录；
- 最终 `.docx`；
- 最终 `.pdf`。

Markdown 中允许使用 LaTeX 作为数学表达，但必须放在正确的数学环境中；最终 `.docx/.pdf` 则禁止把 LaTeX 源码直接当普通文本写入正文或表格。

例如以下内容：

```latex
x_{icst}
Q_{cst}=\sum_p u_{pcs}x_{pcst}
\Pi_\omega
```

在 Markdown 中应写成规范数学环境：

```markdown
$x_{icst}$

$$
Q_{cst}=\sum_p u_{pcs}x_{pcst}
$$

$\Pi_\omega$
```

最终 Word/PDF 中必须显示为正确的下标、求和、希腊字母和数学结构，而不是出现 `_`、`{}`、`\sum`、`\omega` 等源码痕迹。

如果最终 Word/PDF 存在未渲染公式，状态标记：

```text
FORMULA_RENDERING_FAILED
```

如果 Markdown 教程中存在错误数学环境、裸 LaTeX 或公式说明缺失，标记：

```text
FORMULA_DOCUMENTATION_FAILED
```

修复前不得视为教程完整。

---

# 1. 覆盖范围

该规则适用于所有数学内容，包括：

- 行内变量；
- 独立公式；
- 目标函数；
- 约束条件；
- 求和、积分、极值、概率、期望；
- 分式、根式、上下标；
- 矩阵、向量、分段函数；
- 希腊字母；
- 公式编号；
- 符号说明表中的数学列；
- 图表标题、表头中真正需要数学排版的变量；
- 教程、论文和附录中的数学表达。

特别注意：**符号说明表不是普通文本例外。**

例如应显示数学形式 `$A_i$`、`$x_{icst}$`、`$z_{cst}$`、`$\Pi_\omega$`，不能在 Markdown 中写成脱离数学环境的普通字符串 `A_i`、`x_{icst}`、`Π_ω` 或带花括号的伪 LaTeX。

# 2. Markdown 教程中的公式格式

教程类 Markdown 必须使用规范 LaTeX 数学环境。

## 2.1 行内公式

短变量、参数和简短关系统一使用：

```markdown
$x_{icst}$
```

例如：

```markdown
其中，$x_{icst}$ 表示地块 $i$ 在年份 $t$、季次 $s$ 下种植作物 $c$ 的面积。
```

禁止：

```text
x_{icst}
```

直接作为普通正文数学表达。

## 2.2 独立公式

完整模型公式、目标函数、约束、状态转移、损失函数等统一使用：

```markdown
$$
Q_{cst}=\sum_p u_{pcs}x_{pcst}
$$
```

不使用裸 LaTeX 行：

```text
Q_{cst}=\sum_p u_{pcs}x_{pcst}
```

也不要用代码块冒充数学公式。

## 2.3 复杂结构

涉及以下内容时必须使用标准 LaTeX：

- 分式：`\frac{a}{b}`；
- 根式：`\sqrt{x}`；
- 求和：`\sum_{i=1}^{n}`；
- 积分：`\int_a^b`；
- 极值：`\max`、`\min`；
- 矩阵：`\begin{bmatrix}...\end{bmatrix}`；
- 分段函数：`\begin{cases}...\end{cases}`；
- 希腊字母：`\alpha`、`\beta`、`\omega`、`\Pi`；
- 上下标：`x_i`、`x^{(t)}`、`x_{icst}`。

不得混用普通下划线、Unicode 下标、LaTeX 和手工拼接方式模拟复杂数学结构。

# 3. Markdown 教程必须解释公式

教程不是公式仓库。每个关键公式后必须给出**人能看懂的说明**。

至少覆盖：

1. **这条公式在做什么**；
2. **每个核心变量和参数是什么**；
3. **上下标分别代表什么**；
4. **单位是什么**；
5. **为什么这样建模**；
6. **它与上一条/下一条公式的关系**；
7. **它在代码中的对应位置**。

例如：

```markdown
总产量定义为：

$$
Q_{cst}=\sum_p u_{pcs}x_{pcst}
$$

其中：

- $Q_{cst}$：作物 $c$ 在季次 $s$、年份 $t$ 的总产量，单位为斤；
- $u_{pcs}$：地块类型 $p$ 上作物 $c$ 在季次 $s$ 的亩产量，单位为斤/亩；
- $x_{pcst}$：对应种植面积，单位为亩；
- 求和符号表示对所有适用地块类型 $p$ 汇总。

这条公式把“单位面积产量 × 种植面积”汇总成总产量，后续销售约束和利润目标都直接依赖 $Q_{cst}$。

代码对应：`question1/model.py::build_production_expression()`。
```

如果一个公式只是教科书定义且非常简单，也至少解释它在当前问题里的具体含义，不要只抄公式。

---

# 4. 变量与符号说明必须一致

教程中的符号表、正文公式、Python 变量和最终论文必须互相对应。

必须避免：

- 同一符号在不同章节代表不同含义；
- 同一个变量一会儿写 `$x_{icst}$`，一会儿写 `$X_{icst}$`；
- 教程里 `$t$` 表示年份，后文又变成时间步；
- 公式使用 `$Q_{cst}$`，代码解释却说对应 `sales`；
- 参数单位前后不一致。

如果代码变量名为了工程可读性与数学符号不同，应明确给出映射，例如：

```markdown
数学符号 $x_{icst}$ 在代码中对应 `plant_area[i, c, s, t]`。
```

---

# 5. 符号说明表

Markdown 符号说明表中的数学列必须使用数学环境，例如：

| 符号 | 含义 | 单位 |
|---|---|---|
| $t$ | 年份索引 | 年 |
| $A_i$ | 地块 $i$ 的面积 | 亩 |
| $x_{icst}$ | 种植面积决策变量 | 亩 |
| $y_{icst}$ | 是否启用该种植方案的 0-1 变量 | - |
| $u_{ics}$ | 基准亩产量 | 斤/亩 |
| $Q_{cst}$ | 总产量 | 斤 |
| $z_{cst}$ | 正常价格销量 | 斤 |
| $\omega$ | 随机场景编号 | - |
| $\Pi_\omega$ | 场景总利润 | 元 |

不要把数学列写成普通字符串。

最终 DOCX 中，这一列中的每个单元格都应插入真正的数学对象或经过验证的数学渲染，不得直接复制 Markdown/LaTeX 字符串。

---

# 6. 教程中必须覆盖哪些公式

每个实际子问题的 Markdown 教程至少应覆盖本问真正使用的：

- 核心变量定义；
- 目标函数；
- 主要约束；
- 数据转换公式；
- 关键中间量；
- 预测/优化/评价核心关系；
- 损失函数或评价指标；
- 必要的检验统计量；
- 问题间传递公式。

如果某问没有复杂公式，也应明确说明它主要依赖算法流程/规则，而不是为了“有公式”硬造数学表达。

严禁为了教程看起来高级而添加实际模型没有使用的公式。

---

# 7. 公式与代码对应

教程中的关键公式应尽量能追到具体源码位置。

推荐写法：

```markdown
代码对应：`src/question2/model.py::objective()`
```

或：

```markdown
代码对应：
- 目标函数：`model.py::build_objective()`
- 约束 (3)：`constraints.py::add_capacity_constraints()`
```

这样队员可以从公式直接跳到实现，真正学会“数学模型如何变成代码”。

# 8. Markdown 公式质量检查

生成教程后必须检查：

- 行内数学是否放在 `$...$` 中；
- 独立公式是否放在 `$$...$$` 中；
- 是否存在正文里的裸 `x_{...}`、`\sum`、`\frac`、`\omega` 等；
- 是否存在未闭合 `$` / `$$`；
- 是否存在明显 LaTeX 语法错误；
- 是否出现代码块冒充数学公式；
- 每个关键公式是否有说明；
- 符号表与正文是否一致；
- 单位是否一致；
- 公式是否与最终代码一致。

发现问题标记：

```text
FORMULA_DOCUMENTATION_FAILED
```

修复后才算教程完整。

# 9. DOCX：优先使用原生 Office 数学公式

最终 Word 优先使用 **OMML（Office Math Markup Language）** 数学对象。

## 推荐路线 A：Pandoc 转 DOCX

如果论文母稿以 Markdown + LaTeX 数学维护，优先：

```text
Markdown / LaTeX 数学源
        ↓
Pandoc
        ↓
DOCX（OMML 原生公式）
```

当用户提供官方 `.docx` 模板时，优先通过 `--reference-doc` 或等效方式继承模板样式，同时让数学表达转换为 Word 原生公式。

核心原则：**不能把 `$x_{icst}$` 直接写成普通 Word 文本。**

## 推荐路线 B：程序化 DOCX + OMML

如果使用 `python-docx` 等程序化方式生成 Word：

- 禁止 `paragraph.add_run(latex_string)` 直接塞 LaTeX；
- 应把数学源转换为 MathML / OMML，再插入 `m:oMath` 或 `m:oMathPara`；
- 可以使用可靠的 LaTeX → MathML → OMML 转换链；
- 或构造合法 OMML 数学对象。

## 不允许

以下方式不得作为正式公式方案：

- 把 `x_{icst}`、`\frac{a}{b}`、`\sum` 作为普通文字；
- 用手打 `_` 模拟下标；
- 用多个普通字符拼一个复杂公式；
- 公式实际是代码字符串，只靠字体“看起来像数学”。

---

# 10. 公式图片只作为兼容性 fallback

如果当前环境无法可靠生成 OMML，但必须完成 Word，可将公式渲染为高质量**矢量**对象作为 fallback。

优先：

```text
SVG / EMF / 其他可可靠嵌入 Word 的矢量格式
```

最后才考虑高分辨率位图。

公式图片必须：

- 字体清晰；
- 与正文基线和字号协调；
- 白底/透明背景自然；
- 不模糊；
- 不裁切上下标；
- 不出现巨大留白；
- PDF 导出后仍然清晰。

只要环境能够稳定生成 OMML，就不应为了省事把所有公式截图化。

---

# 11. 独立公式排版

独立公式默认：

- 居中；
- 上下留有适当间距；
- 公式编号统一，例如 `(1)`、`(2)`；
- 正文引用编号与公式实际编号一致；
- 长公式必要时合理换行，但不能拆坏数学结构；
- `max`、`min`、`s.t.`、求和上下限、矩阵和分段函数必须按数学规范排版。

例如：

```latex
\max \Pi_1
=\sum_{c,s,t} P_{cst}z_{cst}
-\sum_{p,c,s,t} C_{pcs}x_{pcst}
```

最终文件中应以完整数学公式呈现，而不是普通正文字符。

---

# 12. PDF 生成规则

PDF 不得只是把错误的 Word 继续导出一遍。

推荐：

```text
已通过公式验收的 DOCX
        ↓
可靠 PDF 导出
        ↓
PDF 二次公式检查
```

如果当前 Word → PDF 工具会破坏 OMML、字体、上下标或公式布局：

- 更换导出方式；
- 或从同一份 Markdown / LaTeX 数学母稿独立生成 PDF；
- 但 Word 和 PDF 的公式内容、编号、符号、正文结果必须一致。

不能接受“Word 有问题，PDF 也一样”作为完成状态。

---

# 13. 自动残留扫描

最终 DOCX/PDF 生成后必须做一次公式源码残留扫描。

重点检查以下高风险模式：

```text
_{
^{
\frac
\sum
\prod
\int
\sqrt
\alpha
\beta
\omega
\Pi
\begin{
\left
\right
$...
\(...\)
\[...\]
```

也检查普通文本中的可疑形式：

```text
x_{...}
A_i
z_{...}
```

注意：扫描结果需要结合上下文判断，不能把文件路径中的下划线等误报成公式问题。

发现正文、表格、标题或公式区域仍有 LaTeX 源码时，必须修复后重新导出。

---

# 14. DOCX 结构验收

如果 Word 采用 OMML，应至少检查：

- DOCX 内存在 `m:oMath` / `m:oMathPara`；
- 数学对象数量与论文中预期公式数量大致一致；
- 符号说明表中的数学变量没有全部退化为普通文本；
- 公式编号和正文引用仍然正确。

可以解压 `.docx` 并检查 `word/document.xml` 等 XML 结构。

只检测“文件能打开”不算验收通过。

---

# 15. 视觉验收

程序检查后还必须进行视觉检查。

至少检查所有含重要公式的页面，重点看：

- 上下标是否正确；
- 求和上下限是否正确；
- 分式是否完整；
- 希腊字母是否正确；
- 公式是否被裁切；
- 表格中的数学符号是否正常；
- 公式字号是否与正文协调；
- Word 与 PDF 是否一致；
- 公式是否与原始数学含义一致。

数学意义正确但视觉排版坏掉，也不能交付。
