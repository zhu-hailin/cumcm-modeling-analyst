# 第二阶段解题模式

## 模式选择

第一阶段完成精简分析、探索性研究、逐问推荐和整题路线后，如果用户尚未提前指定，AI 需要让用户明确选择：

1. **逐题深度求解**：推荐用于 Codex、本地执行和正式比赛深挖；
2. **一次性完整求解**：推荐用于 Chat 模式或队伍前期快速获得整题参考。

选择时使用自然口语简要说明差别，不需要把完整协议贴给用户。

如果用户已经明确“逐题”“一次性”“全部一起做”等，就直接遵循，不重复追问。

---

# 模式 A：逐题深度求解

状态可记为 `STAGE_2_QUESTION_BY_QUESTION`，但状态名默认不需要展示给用户。

使用 [../assets/QUESTION_BY_QUESTION_SOLUTION_TEMPLATE.md](../assets/QUESTION_BY_QUESTION_SOLUTION_TEMPLATE.md)。

逐题模式的底层流程不变：

```text
问题1
↓
完整闭环
↓
阶段闸门：推进 / 有价值的扩展研究
↓
问题2
↓
...
↓
问题n
↓
全局回查与总结
↓
最终参考论文
↓
四包交付
```

## 每一问都必须完整闭环

进入问题 k 时，重新阅读：

- 原题中问题 k 的准确要求；
- 全局题意、公共约束和共享变量；
- 问题 1...k-1 已经得到的真实结果；
- 当前问与前一问、后一问以及整题目标的关系；
- 当前新证据是否会反过来影响前面接口或整体路线。

随后后台完成：

1. 本问目标回查；
2. 上下关联探索；
3. 必要的问题级探索性研究；
4. 本问最终模型；
5. 完整 Python 实现；
6. 实际运行与结果；
7. 合适的验证；
8. 代码解析；
9. 本问资料与文献；
10. 直接回答本问；
11. 向下一问交接。

这些步骤必须完成，但不需要在聊天窗口逐条播报。

## 强化上下关联

逐题模式不允许把每一问当独立项目。必须检查：

- 上一问输出是否直接成为当前问输入；
- 当前问是否需要重新解释上一问结果；
- 当前问发现的新结构是否会改变后续模型；
- 当前问的新证据是否推翻此前某个假设、参数或接口；
- 是否需要回到上一问做小幅修订；
- 当前输出如何被下一问实际使用。

若核心路线被推翻，触发 `ROUTE_REOPEN_REQUIRED`。

# 每问完成后的阶段闸门

只有当前问题已经完整闭环后，才可以进入阶段闸门。

聊天窗口默认只用几句口语告诉用户：

- 我刚完成了什么；
- 最重要的真实发现；
- 这个发现有什么用；
- 我建议推进还是值得再研究一轮；
- 完整内容在哪个 Markdown。

不要机械输出：

```text
问题1已完成：模型、代码、运行结果、验证、代码解析和资料均已整理。
是否继续问题2？
```

更自然地交流，例如：

```text
问题一这边我已经跑通了，主模型比 baseline 稳不少，而且参数变化下结果也没怎么飘，这一问现在是能交付的。

我还看到一个可能值得多看一轮的点：XXX，它可能会影响问题二的输入。如果你们想再冲一下我继续；如果更想赶进度，我们直接上问题二也完全可以。完整过程我放进问题1_研究记录.md 了。
```

示例只表示语气，不得机械复制。

# 扩展研究不是必做项

核心流程已经完成后，扩展研究才是可选项。

AI 建议继续研究前，必须明确：

1. **研究问题**：具体要验证什么；
2. **研究价值**：为什么值得花时间；
3. **决策影响**：可能改变模型、参数、结论还是下一问接口；
4. **停止条件**：达到什么条件就停止。

任何一项说不清楚，就不应建议继续。

禁止：

- 为了多一个模型而跑模型；
- 为了创新而制造创新；
- 为了实验丰富而堆图、堆检验；
- 把噪声包装成规律；
- 为了“完成扩展研究”编造结果。

扩展研究合法结果：

- `MEANINGFUL_FINDING`：确实得到会改变决策或增强证据的新发现；
- `NO_MEANINGFUL_FINDING`：认真研究但没有值得采用的新发现；
- `INCONCLUSIVE`：当前证据不足，无法可靠判断。

没有新发现完全正常。如果继续研究大概率只是在堆实验，应主动建议停止。

# 每问文件沉淀

边做边保存，不要最后凭记忆回填：

```text
源码/赛题A/问题k/
├── src/
├── exploration/
├── data/
└── outputs/

题目详解/问题k/问题k_完整教程.md
其他/文献与来源/问题k_资料与文献.md
其他/赛时协作/研究决策日志.md
```

聊天窗口省略的研究细节必须进入 Markdown。

# 模式 B：一次性完整求解

状态可记为 `STAGE_2_ONE_PASS`。

适合：

- Chat 模式；
- 比赛前期快速获得整题完整参考；
- 队伍需要迅速比较整题逻辑和工作量；
- 用户明确不希望问题之间频繁暂停。

流程：

```text
问题1 → 问题2 → ... → 问题n → 全局验证 → 原题回查 → 教程/论文/四包交付
```

一次性模式仍必须：

- 使用第一阶段探索证据；
- 按依赖关系完成各问；
- 每问有完整模型、代码、实际结果和验证；
- 显式记录各问输入输出接口；
- 新证据推翻路线时允许 `ROUTE_REOPEN_REQUIRED`；
- 不因为追求速度而降低真实性、代码完整性或文献核验标准。

一次性模式不需要每问都停下来询问，但遇到真正会改变路线、重大风险或关键异常时，应像队友一样主动提醒用户。

它与逐题模式的区别主要是交互节奏和研究组织方式，不是质量底线不同。

---

# 全部问题完成后的原题回查

无论哪种模式，最终论文和四包交付前必须重新读取原题，并建立要求回查表：

| 原题要求 | 对应问题 | 最终答案/结果 | 对应代码/输出 | 是否完整回答 | 备注 |
|---|---|---|---|---|---|

检查动作词、子要求、边界条件、指定格式、单位、问题之间真实传递和结论支持范围。

没有完成回查，不得进入 `FINAL_DELIVERY`。
