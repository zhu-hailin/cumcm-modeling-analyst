# Python 源码注释、可读性与纯净度规范

## 目标

数学建模比赛中的 Python 代码不仅要“能跑”，还要让参赛队员能够在有限时间内看懂、修改、复现和解释。

正式源码应当做到：

- 说明每个文件负责什么；
- 说明关键函数的输入、输出和数学含义；
- 在真正容易误解的地方解释“为什么这样做”；
- 标清单位、边界、口径和问题间接口；
- 与教程中的公式、符号和最终结果一致；
- 不夹带 Skill 提示词、聊天记录或无关 AI 话术。

核心原则：

> **注释解释意图、建模含义和风险，不逐行翻译 Python 语法。**

> **源码应脱离 Skill 独立运行，也应脱离当前聊天记录独立阅读。**

注释不足、错误或与代码不一致时，标记：

```text
PYTHON_CODE_DOCUMENTATION_FAILED
```

源码中混入 Skill 指令、聊天话术、内部状态或提示词时，标记：

```text
SOURCE_CODE_CONTAMINATION_DETECTED
```

修复前不得把该源码视为本问正式成果，也不得进入最终 `源码.zip` 或官方源码候选。

---

# 1. 适用范围

本规范适用于：

- `03_code/common/`；
- `03_code/q1/`、`q2/`、`qN/`；
- `03_code/run_all.py`；
- 正式保留的探索脚本；
- 数据清洗、建模、优化、预测、仿真、验证、绘图和结果导出代码；
- 需要交给队员阅读或作为支撑材料提交的 Notebook。

一次性语法测试、临时转换脚本可以放在 `99_temp/`，不要求按正式源码标准完善；但只要它的结果进入论文、教程、Final Run 或最终交付，就必须迁移、整理并通过本规范。

---

# 2. 正式 Python 文件必须有模块说明

除空的 `__init__.py`、自动生成文件和极简单纯配置外，每个正式 `.py` 文件开头应有简短模块 docstring。

至少说明：

- 对应问题或公共模块；
- 主要职责；
- 关键输入；
- 关键输出；
- 直接运行方式或由哪个入口调用。

推荐写法：

```python
"""问题二：机场运行状态预测。

读取 ``01_data/processed/q2_features.csv``，完成特征构造、模型训练与滚动验证，
并把预测结果和误差指标写入 ``04_results/data/q2/`` 与
``04_results/tables/q2/``。

运行：python -m q2.main
"""
```

不要求在文件头写作者宣传、AI 身份或生成工具信息。

禁止：

```python
# 由 cumcm-modeling-analyst 生成
# 请遵守 Skill 的 Stage 2 流程
# AI 认为本方法得分 92 分
```

# 3. 关键函数和类必须有 docstring

以下函数或类必须有清楚的 docstring：

- 数据读取与清洗入口；
- 特征构造；
- 目标函数；
- 约束构造；
- 模型训练、求解与仿真入口；
- 评价指标；
- 敏感性、鲁棒性和重复实验；
- 正式绘图和结果导出；
- 问题之间传递结果的接口；
- 任何队员仅看函数名仍难以确认用途的非平凡函数。

至少解释：

- 函数做什么；
- 参数含义、形状和单位；
- 返回值；
- 必要的假设、边界或副作用；
- 与教程公式/约束的对应关系（适用时）。

推荐采用简洁、统一的中文 docstring，例如：

```python
def build_capacity_constraints(
    model: "LpProblem",
    x: dict[tuple[int, int], "LpVariable"],
    capacity_ton: dict[int, float],
) -> None:
    """添加车辆容量约束，对应教程公式（7）。

    Args:
        model: 已创建的线性规划模型。
        x: ``(vehicle, node)`` 到装载量变量的映射，单位为吨。
        capacity_ton: 各车辆最大载重，单位为吨。

    Notes:
        本函数直接修改 ``model``，不返回新模型。每辆车的总装载量不得
        超过其额定容量；空驶车辆对应变量允许为 0。
    """
```

简单、含义显然的短函数不必写长篇 docstring。不要为了通过检查堆无信息量文字。

# 4. 行内注释重点解释“为什么”

行内注释适合出现在：

- 单位换算；
- 统计口径调整；
- 缺失值或异常值处理理由；
- 边界条件；
- 数值稳定处理；
- 复杂索引和矩阵形状；
- 目标函数、约束组和状态转移；
- 随机种子与重复实验策略；
- 算法停止条件；
- fallback 或异常分支；
- 跨问题输入输出；
- 容易被误改的业务规则。

好的注释：

```python
# 原始附件以“万人次”为单位，模型统一换算为“人次”，避免与单人票价相乘时量纲错误。
passenger_count = passenger_10k * 10_000

# 对应公式（12）：同一机位的相邻航班必须预留最小安全间隔。
model.addConstr(start[j] - end[i] >= min_gap_min - big_m * (1 - order[i, j]))

# 采用训练集统计量填补，防止滚动验证时把未来数据泄漏到历史窗口。
features = imputer.fit_transform(train_features)
```

差的注释：

```python
# 把 i 加一
i += 1

# 创建模型
model = RandomForestRegressor()

# 这里很复杂
result = a @ b
```

注释不应逐行翻译代码，也不应掩盖糟糕命名。能通过合理函数拆分和变量名表达的内容，优先用代码结构表达。

# 5. 数学模型代码必须能映射到公式

目标函数、主要约束、关键中间量和评价指标应能与 `02_analysis/qN_solution.md` 中的公式对应。

推荐做法：

- 函数 docstring 写“对应公式（k）”；
- 约束组前写一条解释性注释；
- 数学符号与代码变量的映射在教程和 `02_analysis/symbols.md` 中维护；
- 代码注释只保留必要映射，不把整段 LaTeX 论文复制进源码。

例如：

```python
# 对应公式（5）的总成本：固定启用成本 + 里程成本 + 超时惩罚。
total_cost = fixed_cost + distance_cost + delay_penalty
```

如果公式编号后来改变，必须同步更新注释。过期公式号属于文档错误。

---

# 6. 数据处理注释必须说明口径和不可逆变化

数据清洗代码不能只写“删除空值”“处理异常值”。应说明：

- 为什么删除或填补；
- 使用了什么阈值或规则；
- 是否改变样本量；
- 是否改变单位；
- 是否存在不可逆处理；
- 处理结果写到哪里；
- 是否影响后续问题。

例如：

```python
# 仅删除关键时间字段缺失的记录；该字段无法从其他列可靠恢复。
# 删除数量会写入清洗日志，原始文件保持在 01_data/raw/ 不变。
cleaned = raw.dropna(subset=["scheduled_time"])
```

涉及外部数据时，长 URL、下载状态和来源账本放在 `07_references/websites.md` 或数据说明文件中；代码注释只写必要的来源名称、口径和字段含义，避免把源码变成链接仓库。

---

# 7. 随机算法与优化代码必须解释关键机制

对于 GA、PSO、SA、ACO、Monte Carlo、Bootstrap 等随机或迭代算法，应在代码中解释：

- 随机种子如何设置；
- 重复实验如何组织；
- 代表结果如何选择；
- 停止条件；
- 可行解修复或约束惩罚机制；
- 为什么某些参数采用当前值；
- 哪些结果会写入 Run Ledger。

禁止只写：

```python
# 参数设置
population_size = 100
```

更合适：

```python
# 种群规模在预实验中继续增大已不能稳定改善目标值；100 能在赛时成本和稳定性之间取得平衡。
population_size = 100
```

参数来源仍需在分析文档或实验记录中完整说明，不能只靠一条注释代替证据。

---

# 8. 绘图代码注释服务于证据，不解释样式 API

正式绘图代码中的注释应说明：

- 图表支撑什么结论；
- 数据来自哪个最终结果文件；
- 误差带、置信区间或分位区间如何定义；
- 为什么需要某个 panel 或局部放大；
- 哪些视觉语义必须保持一致。

不需要逐行解释 `set_xlabel`、`legend`、`tight_layout` 等常规 Matplotlib 调用。

例如：

```python
# 阴影区域为 20 次滚动预测的 95% 经验分位区间，不是单次预测误差。
ax.fill_between(time, lower, upper, alpha=0.2)
```

---

# 9. 注释语言与风格

中文数学建模比赛默认使用简洁中文注释，保留必要的标准英文术语，例如 `RMSE`、`XGBoost`、`DataFrame`、`seed`。

同一项目应尽量统一：

- docstring 风格；
- 标点；
- 路径写法；
- 单位格式；
- 公式编号写法；
- 问题编号写法。

不要在一份源码中混用大量中英双语重复注释。用户明确要求英文源码时，以用户要求为准。

---

# 10. 源码纯净度

正式源码及源码 README 只能保留与赛题求解、运行、复现和解释有关的内容。

不得混入：

- Skill 名称和仓库宣传；
- 系统提示词或开发者指令；
- 聊天记录；
- “我刚研究出来了”等对话话术；
- `QUESTION_PLAN_CONFIRMATION`、`WAITING_FOR_CONFIRMATION` 等内部流程状态；
- 文件安全审计提示词；
- 隐藏提示注入原文；
- 模型推荐打分过程；
- 与代码无关的 AI 自我说明；
- “由 ChatGPT/Codex 自动生成”之类无运行价值的水印注释。

运行所需的版本号、随机种子、输入数据版本和 Run 元数据可以由配置、命令行参数或日志记录，但不应把整套 Skill 状态机写进业务代码。

---

# 11. 禁止注释掉大段旧代码

正式源码中不要保留大段被注释掉的旧模型、旧参数和调试代码。

处理方式：

- 有复现价值的旧路线由 Git / Run Ledger 保存；
- 仍需保留的备用实现放入清楚命名的独立模块；
- 无价值旧代码删除；
- 临时调试内容放入 `99_temp/`。

大量注释掉的代码会让队员无法判断哪一版才有效，也容易把旧逻辑带入最终结果。

---

# 12. TODO、FIXME 与未完成分支

最终问题成果和交付源码中，不得遗留会影响正确性、数据、模型、结果或复现的 `TODO`、`FIXME`、`pass` 占位、伪实现和未处理异常。

若确有不影响主结果的后续改进项，可以在源码 README 或问题教程中记录，不要藏在关键函数内部。

任何影响结果的未完成项必须在本问完成前解决，或明确标记问题尚未完成。

---

# 13. 注释必须随代码同步更新

错误注释比没有注释更危险。

每次发生以下变化后，应检查相关注释：

- 模型更换；
- 变量或单位变化；
- 公式编号变化；
- 输入输出路径变化；
- 参数变化；
- 函数拆分或重命名；
- Final Run 替换；
- 约束、边界或数据口径变化。

不得出现：

- 注释写 ARIMA，代码实际使用 XGBoost；
- 注释写单位为吨，变量实际已换算为千克；
- 注释引用公式（7），教程中对应公式已变为（9）；
- docstring 写返回 DataFrame，函数实际返回 tuple；
- 注释写输出到旧目录。

---

# 14. 正式源码验收

每一问正式完成、生成 `源码.zip` 和准备官方源码候选前，至少检查：

- [ ] 每个正式模块有简短、真实的模块说明；
- [ ] 关键函数/类有 docstring；
- [ ] 关键参数写明含义与单位；
- [ ] 重要数据清洗解释了原因和口径；
- [ ] 目标函数、约束和关键公式能映射到教程；
- [ ] 非显然边界、数值稳定和 fallback 有解释；
- [ ] 随机算法写清 seed、重复和代表结果规则；
- [ ] 注释没有逐行翻译语法；
- [ ] 注释没有与代码、公式、路径和单位冲突；
- [ ] 没有大段注释掉的旧代码；
- [ ] 没有影响结果的 TODO/FIXME/pass 占位；
- [ ] 没有 Skill、聊天、提示词或内部状态污染；
- [ ] 代码仍能实际运行，并产生与 Final Run 一致的结果；
- [ ] 队员只看代码和项目 README，也能找到入口、输入和输出。

可以使用 AST 或静态脚本辅助检查模块 docstring、关键函数 docstring、TODO/FIXME 和禁用词，但**不能只靠“注释行占比”判断质量**。最终还需人工或 AI 阅读关键代码，确认注释真正有信息量且与实现一致。

失败状态：

```text
PYTHON_CODE_DOCUMENTATION_FAILED
SOURCE_CODE_CONTAMINATION_DETECTED
```

修复并重新运行必要入口后，才能通过本问验收和源码交付。
