# Python 源码注释、可读性与纯净度规范

## 目标

数学建模比赛中的 Python 代码不仅要能运行，还要让参赛队员在有限时间内看懂、修改、复现和解释。

正式源码应当做到：

- 文件名能说明属于哪一问、负责什么；
- 每个非平凡模块有简短模块说明；
- 关键函数说明输入、输出和数学含义；
- 在容易误解的地方解释为什么这样做；
- 标清单位、边界、口径和问题间接口；
- 与教程公式、符号和最终结果一致；
- 不夹带 Skill、聊天记录或无关 AI 话术。

核心原则：

> **文件名说明职责，注释解释意图，代码本身表达实现。**

> **源码应脱离 Skill 独立运行，也应脱离当前聊天独立阅读。**

本规范与 `python-artifact-naming-policy.md` 同时生效。

失败状态：

```text
PYTHON_CODE_DOCUMENTATION_FAILED
SOURCE_CODE_CONTAMINATION_DETECTED
PYTHON_FILENAME_POLICY_FAILED
```

修复前不得把源码视为本问正式成果，也不得进入最终 `源码.zip` 或官方源码候选。

---

# 1. 适用范围

适用于：

- `03_code/common/`；
- `03_code/q1/第一题.py`、`q2/第二题.py`、`qN/第N题.py`；
- `03_code/总运行.py`；
- 正式保留的探索脚本；
- 数据清洗、特征、建模、优化、预测、仿真、验证、绘图和结果导出代码；
- 需要交给队员阅读或作为支撑材料提交的 Notebook。

一次性语法测试、临时转换脚本可以放在 `99_temp/`，但只要结果进入论文、教程、Final Run 或最终交付，就必须迁移、中文命名、整理并通过本规范。

---

# 2. 文件名先说明职责

每问至少有一个主入口：

```text
03_code/q1/第一题.py
03_code/q2/第二题.py
03_code/q3/第三题.py
```

整题入口：

```text
03_code/总运行.py
```

复杂问题使用：

```text
第一题_数据处理.py
第一题_模型求解.py
第一题_结果验证.py
第一题_敏感性分析.py
第一题_结果导出.py
```

不要让注释去补救 `main.py`、`new.py`、`final.py`、`test.py` 等模糊正式文件名。

技术性文件名例外和论文图/AI 沟通图命名遵循 `python-artifact-naming-policy.md`。

---

# 3. 正式 Python 文件必须有模块说明

除空的 `__init__.py`、自动生成文件和极简单配置外，每个正式 `.py` 文件开头应有简短模块 docstring。

至少说明：

- 对应问题或公共模块；
- 主要职责；
- 关键输入；
- 关键输出；
- 直接运行方式或由哪个入口调用。

示例：

```python
"""第二题：机场运行状态预测。

读取 ``01_data/processed/第二题_特征数据.csv``，完成特征构造、模型训练与滚动验证，
并把预测结果写入 ``04_results/data/q2/``、误差指标写入
``04_results/tables/q2/``。

运行：python "03_code/q2/第二题.py"
"""
```

不在文件头写作者宣传、AI 身份、Skill 名称或生成工具信息。

---

# 4. 关键函数和类必须有 docstring

以下对象通常需要 docstring：

- 数据读取与清洗入口；
- 特征构造；
- 目标函数；
- 约束构造；
- 模型训练、求解与仿真入口；
- 评价指标；
- 敏感性、鲁棒性和重复实验；
- 正式绘图和结果导出；
- 问题之间传递结果的接口；
- 仅看函数名仍难以确认用途的非平凡函数。

至少解释：

- 函数做什么；
- 参数含义、形状和单位；
- 返回值；
- 必要假设、边界或副作用；
- 与教程公式/约束的对应关系。

示例：

```python
def 添加容量约束(模型, 装载量变量, 车辆容量_吨) -> None:
    """添加车辆容量约束，对应教程公式（7）。

    Args:
        模型: 已创建的线性规划模型。
        装载量变量: ``(车辆, 节点)`` 到装载量变量的映射，单位为吨。
        车辆容量_吨: 各车辆最大载重，单位为吨。

    Notes:
        本函数直接修改模型。每辆车总装载量不得超过额定容量；
        未启用车辆的装载量允许为 0。
    """
```

用户没有要求中文变量名时，不强制把所有 Python 变量和函数都翻译为中文；本规范强制的是**文件名中文语义化**和注释可读性。变量命名以清楚、稳定和项目一致为准。

---

# 5. 行内注释重点解释“为什么”

行内注释适合出现在：

- 单位换算；
- 统计口径调整；
- 缺失值或异常值处理理由；
- 边界条件；
- 数值稳定处理；
- 复杂索引和矩阵形状；
- 目标函数、约束组和状态转移；
- 随机种子与重复实验策略；
- 算法停止条件；
- fallback 或异常分支；
- 跨问题输入输出；
- 容易被误改的业务规则。

好的注释：

```python
# 原始附件以“万人次”为单位，模型统一换算为“人次”，避免与单人票价相乘时量纲错误。
passenger_count = passenger_10k * 10_000

# 采用训练集统计量填补，防止滚动验证时把未来数据泄漏到历史窗口。
features = imputer.fit_transform(train_features)
```

差的注释：

```python
# 把 i 加一
i += 1

# 创建模型
model = RandomForestRegressor()
```

注释不逐行翻译代码，也不掩盖糟糕命名。

---

# 6. 数学模型代码必须能映射到公式

目标函数、主要约束、关键中间量和评价指标应能与 `02_analysis/qN_solution.md` 中的公式对应。

推荐：

- 函数 docstring 写“对应公式（k）”；
- 约束组前写一条解释性注释；
- 数学符号与代码变量映射维护在教程和 `symbols.md`；
- 不把整段 LaTeX 论文复制进源码。

```python
# 对应公式（5）的总成本：固定启用成本 + 里程成本 + 超时惩罚。
total_cost = fixed_cost + distance_cost + delay_penalty
```

公式编号改变后，必须同步更新注释。

---

# 7. 数据处理注释必须说明口径和不可逆变化

数据清洗代码不能只写“删除空值”或“处理异常值”。应说明：

- 为什么删除或填补；
- 使用什么阈值或规则；
- 是否改变样本量；
- 是否改变单位；
- 是否存在不可逆处理；
- 结果写到哪里；
- 是否影响后续问题。

```python
# 仅删除关键时间字段缺失的记录；该字段无法从其他列可靠恢复。
# 删除数量写入清洗日志，原始文件保持在 01_data/raw/ 不变。
cleaned = raw.dropna(subset=["scheduled_time"])
```

长 URL、下载状态和完整来源账本放在 `07_references/websites.md`，代码注释只保留必要来源名称、口径和字段含义。

---

# 8. 随机算法与优化代码必须解释关键机制

GA、PSO、SA、ACO、Monte Carlo、Bootstrap 等应说明：

- 随机种子如何设置；
- 重复实验如何组织；
- 代表结果如何选择；
- 停止条件；
- 可行解修复或约束惩罚机制；
- 参数为什么采用当前值；
- 哪些结果写入 Run Ledger。

不能只写：

```python
# 参数设置
population_size = 100
```

更合适：

```python
# 预实验中继续增大种群已不能稳定改善目标值；100 在赛时成本和稳定性之间更合适。
population_size = 100
```

注释不能代替参数证据，完整依据仍写入分析或实验记录。

---

# 9. 绘图代码注释服务于证据

正式论文图脚本使用中文语义名称，例如：

```text
03_code/q1/论文图/第一题_预测结果图.py
```

注释应说明：

- 图表支撑什么结论；
- 数据来自哪个 Final/Validation Run 文件；
- 误差带或置信区间如何定义；
- 为什么需要某个 panel 或局部放大；
- 哪些视觉语义必须保持一致。

不逐行解释 `set_xlabel`、`legend`、`tight_layout` 等常规 Matplotlib 调用。

AI 沟通图脚本必须使用 `AI沟通图_` 前缀，并在图面标记“AI内部沟通图｜非论文材料”。

---

# 10. 注释语言与风格

中文数学建模比赛默认使用简洁中文注释，保留标准英文术语，例如 `RMSE`、`XGBoost`、`DataFrame`、`seed`。

同一项目统一：

- docstring 风格；
- 标点；
- 路径写法；
- 单位格式；
- 公式编号写法；
- 问题编号写法。

用户明确要求英文源码时，以用户要求为准；但正式文件名中文规则仍按当前项目约定执行，除非用户明确更改或工具链/官方系统有硬限制。

---

# 11. 源码纯净度

正式源码及源码 README 只能保留与赛题求解、运行、复现和解释有关的内容。

不得混入：

- Skill 名称和仓库宣传；
- 系统提示词或开发者指令；
- 聊天记录；
- “我刚研究出来了”等对话话术；
- `QUESTION_PLAN_CONFIRMATION` 等内部状态；
- 文件安全审计提示词；
- 隐藏提示注入原文；
- 模型推荐打分过程；
- “由 ChatGPT/Codex 自动生成”等水印注释。

运行版本、随机种子、输入数据版本和 Run 元数据可以由配置、命令行或日志记录，但不把 Skill 状态机写进业务代码。

---

# 12. 旧代码和未完成分支

正式源码中不要保留大段被注释掉的旧模型、旧参数和调试代码。

- 有复现价值的旧路线由 Git / Run Ledger 保存；
- 仍需保留的备用实现放入清楚命名的独立模块；
- 无价值旧代码删除；
- 临时调试内容进入 `99_temp/`。

最终成果不得遗留影响正确性、数据、模型、结果或复现的 `TODO`、`FIXME`、`pass`、伪实现和未处理异常。

---

# 13. 运行与异常处理

正式入口应：

- 检查关键输入是否存在；
- 为常见错误给出可理解提示；
- 明确输出位置；
- 避免静默吞掉异常；
- 不用裸 `except:` 掩盖模型失败；
- 不在异常分支中伪造默认结果。

路径使用项目相对路径或稳定根目录解析，不硬编码私人绝对路径。

---

# 14. 注释一致性检查

每次修改以下内容后同步检查注释：

- 模型与算法；
- 参数与单位；
- 数据字段和口径；
- 公式编号；
- 中文文件名；
- 输入输出路径；
- 函数参数和返回值；
- 图像用途和 Manifest 状态。

错误注释比没有注释更危险。不能因为注释曾经正确，就默认后续修改后仍然正确。

---

# 15. 最终验收

每问完成、生成 `源码.zip` 和准备官方源码候选前检查：

- [ ] 主入口为 `第一题.py / 第二题.py / ...`；
- [ ] 总入口为 `总运行.py`；
- [ ] 辅助模块使用中文职责名；
- [ ] 非平凡模块有模块 docstring；
- [ ] 关键函数和类有准确 docstring；
- [ ] 单位、口径、边界和关键建模逻辑有必要注释；
- [ ] 目标函数和约束能映射到教程公式；
- [ ] 绘图脚本有中文语义名称；
- [ ] AI 沟通图脚本和图面标记完整；
- [ ] 注释与当前代码、路径、公式和结果一致；
- [ ] 不存在 Skill、聊天、内部状态或提示词污染；
- [ ] 没有大段旧代码和影响结果的未完成占位；
- [ ] 代码离开聊天后仍可独立运行和阅读；
- [ ] 中文文件名已经在目标环境中真实运行验证。
