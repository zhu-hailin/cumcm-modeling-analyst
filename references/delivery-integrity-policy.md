# 交付环境识别与 ZIP 完整性验收规范

## 目标

内部成果的交付方式要根据运行环境调整。Codex 在真实项目目录中工作，Chat 主要通过附件交付，两者不能机械使用同一套路径规则。

任何“ZIP 已生成”都不等于交付完成。

失败状态：

```text
DELIVERY_INTEGRITY_FAILED
```

修复前不得标记 `INTERNAL_DELIVERY_COMPLETE`。

---

# 1. 识别环境

## LOCAL_WORKSPACE_DELIVERY

Codex 或其他获准使用 Codex 布局的本地 Agent，在一个明确的单赛题根目录中直接读写文件、运行命令。

本地目录中的真实文件是主成果，ZIP 是整理和传输副本。

## CHAT_ARTIFACT_DELIVERY

Chat / 云端会话通过下载附件交付。用户主要依赖 ZIP、DOCX、PDF 等下载文件，因此需要更严格的文件名、压缩包和跨平台兼容性检查。

无法判断时采用更严格的 `CHAT_ARTIFACT_DELIVERY` 验收。

---

# 2. Codex 本地交付位置

Codex 工作区完整结构遵循：

[local-workspace-policy.md](local-workspace-policy.md)

默认单赛题根目录例如：

```text
2022-C/
├─ 00_problem/
├─ 01_data/
├─ 02_analysis/
├─ 03_code/
├─ 04_results/
├─ 05_paper/
├─ 06_submission/
├─ 07_references/
└─ 99_temp/
```

本地模式不再默认创建额外顶层 `deliverables/` 或 `modeling_workspace/`。

- AI 参考论文和队员论文工作文件保存在 `05_paper/`；
- 官方提交候选保存在 `06_submission/`；
- 四个内部成果包在用户未指定时保存在 `06_submission/internal_delivery/`；
- 原始代码、数据、图表和日志继续保留在正式工作目录中，不能打包后删除。

用户已经指定其他位置时，以用户要求为准。

---

# 3. 本地原文件是主成果

Codex 不应只生成 ZIP 后删除或移动原目录。

必须保证：

- `00_problem/` 中官方原件仍然存在；
- `01_data/raw/`、`processed/`、`external/` 分层不被打包操作破坏；
- `03_code/` 的最终代码可直接运行；
- `04_results/` 的图、表、数据和日志可直接读取；
- `05_paper/` 中草稿和终稿仍可直接打开；
- ZIP 只是这些已验收材料的副本或筛选集合。

打包失败不得影响本地正式成果。

---

# 4. Chat / 云端交付

Chat 模式下：

- 外层可继续使用四个中文 ZIP 名；
- ZIP 内中文路径必须实际验证；
- 当前压缩工具不能稳定处理中文 entry 时，才回退 ASCII-safe 路径；
- `README.md` 或 `MANIFEST.md` 保留中文映射；
- 平台支持时，论文 DOCX/PDF 应额外独立交付作为兜底。

不能因为运行时目录中有文件，就忽略用户下载后看到空包、乱码或打不开的问题。

---

# 5. 打包前检查

创建每个 ZIP 前先检查源文件，不要边生成边压缩。

至少确认：

- 关键文件真实存在且非 0 字节；
- Markdown 教程已经写完；
- 最终 Python 和依赖说明存在；
- 图表、表格和结果来自最终 Run；
- DOCX/PDF 已通过内容、公式和视觉检查；
- 没有把 `99_temp/` 中的临时文件误当最终成果；
- 没有空目录或占位文件冒充成果；
- 文件写入已经结束。

---

# 6. ZIP 结构测试

每个 ZIP 创建后先执行 CRC / entry 检查，例如：

```bash
unzip -t 参考论文.zip
```

或使用当前语言的 ZIP 库完成等价验证。

`unzip -t` 通过只说明压缩结构基本正常，不代表用户能正常使用。

---

# 7. ZIP 真实解压预检

每个 ZIP 必须实际解压到新的临时目录。Codex 可使用 `99_temp/zip_check/`，检查完成后再清理。

必须从**解压后的副本**检查：

- 文件数量和目录结构；
- 文件名是否乱码；
- 文件大小；
- 关键文件是否存在；
- 是否出现 0 字节文件；
- Markdown、Python、CSV/XLSX 是否可读取；
- DOCX 是否为有效 Office 容器；
- PDF 是否可解析且页数大于 0；
- 图表是否存在、非空并能打开；
- 结果是否来自当前 Final Run，而不是旧产物。

禁止只检查打包前目录后就声称 ZIP 已验证。

---

# 8. MANIFEST 对账

推荐在每个内部成果包根部生成 `MANIFEST.md`：

| 相对路径 | 内容说明 | 文件大小 | SHA-256 | 必须存在 |
|---|---|---:|---|---|

打包后真实解压，再核对：

- 相对路径；
- 字节数；
- SHA-256；
- 必须文件是否齐全。

源目录有文件但解压后丢失、文件名无法对应、大小/hash 异常或关键文件打不开时，标记 `DELIVERY_INTEGRITY_FAILED` 并重新打包。

---

# 9. DOCX / PDF 额外验收

DOCX 至少检查：

- 文件大小大于 0；
- ZIP 容器可打开；
- `word/document.xml` 存在；
- 正文不为空；
- 数学公式规范通过；
- 图表没有缺失。

PDF 至少检查：

- 文件大小大于 0；
- 解析器可打开；
- 页数大于 0；
- 关键公式页和图表页视觉检查通过；
- 内容与对应 DOCX 版本一致。

---

# 10. 最终聊天回复必须真实

只有验证通过后，才可以告诉用户：

- 四个 ZIP 已生成；
- 压缩包可以正常解压；
- 关键论文、源码、图表和数据存在；
- 当前本地路径在哪里。

如果本地成果完整但 ZIP 失败，应明确区分：

> 本地成果文件已经完整，但压缩包预检没有通过，暂时不能把 ZIP 视为完成。

不得把“本地有原文件”说成“ZIP 已验证”。

---

# 11. 最终验收清单

## LOCAL_WORKSPACE_DELIVERY

- [ ] 当前单赛题根目录明确；
- [ ] 工作区符合 `local-workspace-policy.md` 或用户指定结构；
- [ ] 官方原件、原始数据、清洗数据和外部数据没有混放；
- [ ] 最终代码、结果和论文可直接打开；
- [ ] 四个内部 ZIP 从已验收材料创建；
- [ ] ZIP 结构测试通过；
- [ ] ZIP 实际解压通过；
- [ ] 文件名、数量、大小和 hash 正常；
- [ ] 原始成果目录未被删除；
- [ ] `06_submission/` 没有把内部参考材料冒充官方提交文件。

## CHAT_ARTIFACT_DELIVERY

- [ ] 四个 ZIP 实际生成；
- [ ] 内部路径兼容性已确认；
- [ ] 结构测试和实际解压均通过；
- [ ] 解压后数量、文件名和大小正确；
- [ ] DOCX/PDF 可打开且非空；
- [ ] 平台支持时有论文独立文件兜底；
- [ ] 不存在运行时有文件、用户下载包却像空包的情况。

任一关键项失败：

```text
DELIVERY_INTEGRITY_FAILED
```

修复后才能标记：

```text
INTERNAL_DELIVERY_COMPLETE
```
