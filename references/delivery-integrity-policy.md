# 交付环境识别与 ZIP 完整性验收规范

## 目标

最终成果的交付方式必须根据运行环境调整，不能把 Chat / 云端文件下载场景的限制机械套到 Codex 本地工作区，也不能因为 Codex 在本地就省略最终验收。

核心原则：

> **本地工作区以“真实目录”为主，ZIP 是打包副本；Chat / 云端以“可下载文件”为主，ZIP 必须做更严格的跨平台预检。**

无论哪种环境，任何“ZIP 已生成”都不等于交付完成。

失败状态统一记为：

```text
DELIVERY_INTEGRITY_FAILED
```

修复前不得进入 `FINAL_DELIVERY`。

---

# 1. 先识别交付环境

进入最终交付前，先判断当前属于哪一种情况。

## LOCAL_WORKSPACE_DELIVERY

典型场景：Codex / Claude Code / 本地 Agent 在一个明确项目根目录中工作，可以直接读写本地文件并运行命令。

特点：

- 有真实项目根目录；
- 成果文件直接存在于本地磁盘；
- 队员可以绕过 ZIP，直接打开 Word/PDF/Markdown/源码；
- ZIP 主要用于整理、传输和归档，不是唯一成果载体。

## CHAT_ARTIFACT_DELIVERY

典型场景：Chat / 云端会话通过可下载附件向用户交付文件。

特点：

- 用户主要依赖下载链接或 ZIP 获取成果；
- ZIP 内文件名编码、平台下载层、解压软件兼容性更关键；
- 如果 ZIP 打包有问题，用户可能看到“空包”或乱码文件名；
- 因此需要更严格的压缩包预检和兜底文件交付。

如果无法可靠判断，按 `CHAT_ARTIFACT_DELIVERY` 的更严格规则验收。

---

# 2. Codex / 本地工作区：真实目录是主成果

本地 Agent 不应只生成四个 ZIP 后删除原目录。

建议在项目根目录下建立一个固定交付目录：

```text
<project-root>/deliverables/
├── 题目详解/
├── 参考论文/
├── 源码/
├── 其他/
├── 题目详解.zip
├── 参考论文.zip
├── 源码.zip
└── 其他.zip
```

其中：

- 四个未压缩目录是**主成果**；
- 四个 ZIP 是这些目录的**打包副本**；
- 打包失败不得影响已经生成的本地成果；
- 不得为了打 ZIP 把原文件移动、删除或只保留压缩包。

如果用户指定了输出目录，应以用户目录为准，不强行创建 `deliverables/`。

---

# 3. 本地工作区允许中文文件名，但压缩包仍需验证

Codex 本地工作时，不需要为了规避 Chat 下载层的问题强制把所有文件名改成 ASCII。

可以继续使用清晰的中文目录和文件名，例如：

```text
参考论文/
├── A题_参考论文.docx
└── A题_参考论文.pdf
```

但只要还要生成 ZIP，就必须检查：

- 打包工具是否正确记录中文 entry；
- 实际解压后中文名是否正常；
- 关键文件是否丢失；
- 解压后的文件是否能正常读取。

如果当前系统 / 压缩工具对中文 entry 存在兼容问题，可以只对 ZIP 内部使用 ASCII-safe 名称，并在 `README.md` / `MANIFEST.md` 中写中文对应关系；**这是 fallback，不是 Codex 本地模式的默认强制规则。**

---

# 4. Chat / 云端交付：兼容性优先

Chat / 云端模式下，用户通常不能直接访问运行时工作区，所以 ZIP 本身必须足够可靠。

推荐：

- 外层仍保持 `题目详解.zip / 参考论文.zip / 源码.zip / 其他.zip`；
- ZIP 内关键路径优先使用跨平台稳定的命名；
- 如果当前打包工具无法可靠验证中文文件名编码，内部路径回退到 ASCII-safe；
- 在 ZIP 根目录使用 `README.md` 或 `MANIFEST.md` 说明中文含义；
- `参考论文.docx` 与 `参考论文.pdf` 在平台支持时应额外作为独立可下载文件提供，作为 ZIP 故障兜底。

不能因为“ZIP 内原始文件其实存在”就认为用户看到空包不算问题。

---

# 5. 打包前：先检查源目录

无论本地还是 Chat，创建 ZIP 前先检查源目录，而不是边生成边压缩。

至少确认：

- 关键文件实际存在；
- 关键文件不是 0 字节；
- DOCX/PDF 已完成各自质量检查；
- Markdown 教程已完成；
- 源码与结果文件已保存；
- 没有只创建空目录 / 空占位文件；
- 文件写入已经结束。

推荐先形成 staging / deliverables 目录，再统一打包。

---

# 6. ZIP 第一轮：结构完整性测试

每个 ZIP 创建后先做结构测试，例如：

```bash
unzip -t 参考论文.zip
```

或使用当前语言的 ZIP 库进行 CRC / entry 检查。

但必须明确：

> **`unzip -t` 通过只代表压缩结构基本正常，不代表用户真的能正常使用。**

因此还必须执行下一轮真实解压。

---

# 7. ZIP 第二轮：真实解压预检

每个最终 ZIP 必须实际解压到一个新的临时目录。

必须从**解压后的副本**检查：

- 文件数量；
- 目录结构；
- 文件名是否乱码；
- 文件大小；
- 关键文件是否存在；
- 是否出现 0 字节文件；
- Markdown 是否可读取；
- Python / 文本文件是否可读取；
- DOCX 是否为有效 Office ZIP 容器；
- PDF 是否为有效 PDF 且页数大于 0；
- 图表 / 表格文件是否存在且非空。

禁止只检查打包前目录后就声称 ZIP 已验证。

---

# 8. MANIFEST：打包前后对账

推荐在每个成果目录根部生成 `MANIFEST.md`，至少记录：

| 相对路径 | 内容说明 | 文件大小 | SHA-256 | 必须存在 |
|---|---|---:|---|---|

打包后真实解压，再核对：

- 相对路径；
- 字节数；
- SHA-256。

关键成果打包前后应一致。

如果发现：

- 源目录有文件但 ZIP 解压后没有；
- 文件名无法正确对应；
- 文件大小改变；
- hash 不一致；
- 关键文件解压后打不开；

必须标记：

```text
DELIVERY_INTEGRITY_FAILED
```

重新打包。

---

# 9. DOCX / PDF 的额外验收

`参考论文.zip` 必须同时验证论文文件本身，而不仅是 ZIP。

DOCX 至少检查：

- 文件大小 > 0；
- ZIP 容器可以打开；
- `word/document.xml` 存在；
- 正文不是空文档；
- 公式规范检查已通过。

PDF 至少检查：

- 文件大小 > 0；
- PDF 解析器可以打开；
- 页数 > 0；
- 关键公式页 / 图表页视觉检查通过。

如果平台支持独立文件下载，Chat 模式下应同时给出 DOCX/PDF 单独交付作为兜底；Codex 本地模式不需要额外“下载链接”，因为文件本身就在工作区里。

---

# 10. 最终聊天回复必须与真实交付一致

只有在验证通过后，才可以告诉用户：

- 四个 ZIP 已生成；
- 文件可以正常解压；
- 论文文件存在并可打开。

如果某个 ZIP 打包失败，但 Codex 本地未压缩目录正常，应明确说：

> 本地成果目录已经完整，但该 ZIP 的打包预检没有通过，我正在/需要修复压缩包。

不得把“本地原文件存在”说成“ZIP 已验证”。

---

# 11. 最终验收清单

## LOCAL_WORKSPACE_DELIVERY

- [ ] 项目根目录 / 指定输出目录明确；
- [ ] 四个未压缩成果目录真实存在；
- [ ] 关键成果文件可直接打开；
- [ ] 四个 ZIP 已从这些目录创建；
- [ ] 每个 ZIP 结构测试通过；
- [ ] 每个 ZIP 已真实解压一次；
- [ ] 中文文件名 / 内部路径没有异常；
- [ ] 打包前后关键文件一致；
- [ ] 原始成果目录未被删除。

## CHAT_ARTIFACT_DELIVERY

- [ ] 四个 ZIP 实际生成；
- [ ] ZIP 内部路径兼容性已确认；
- [ ] 每个 ZIP 结构测试通过；
- [ ] 每个 ZIP 已真实解压一次；
- [ ] 解压后文件数量 / 文件名 / 大小正确；
- [ ] DOCX/PDF 可打开且非空；
- [ ] 在平台支持时，参考论文 DOCX/PDF 提供独立下载兜底；
- [ ] 不存在“运行时有文件，但用户下载包看起来为空”的情况。

任一关键项失败：

```text
DELIVERY_INTEGRITY_FAILED
```

修复后才能进入 `FINAL_DELIVERY`。
