# Codex 单赛题工作空间规范

## 目标

Codex、Claude Code 等可读写本地目录的 Agent，应同时维护可追溯的运行工作区和队员容易取用的交付目录。工作区容纳研究、代码、数据、运行和历史证据；交付目录只呈现本次范围内当前有效的成果。

用户现有工程、路径和命名优先。未经授权，不删除、覆盖、移动或改名用户原件。

下列结构是完整赛题的职责映射，不是每次任务必须创建的清单。单问小题或局部验证可以只用一个任务目录，放实际源码、结果、运行证据和一份 README/交接；题意、假设、符号及需求验证记录可合并在该交接中，不额外创建独立论文蓝图。真正需要跨问管理/论文时再扩展，验收只针对实际任务范围。真实运行来源和必要的初始附件审计不因此省略。

目录按材料用途组织，不按示例中的软件品牌补齐。Python、MATLAB、R、Excel、SPSS/SPSSPRO 等仅在实际使用时记录；未用 SPSSPRO 的队伍不创建相关目录、工程或操作说明。论文图表另按 [绘图规范](python-visualization-policy.md) 统一由 Python 随问生成。

---

## 1. 默认结构

一个工作区根目录只对应一道已选赛题。以下目录管理运行与权威来源，另设面向队员的交付目录：

```text
2022-C/
├─ README.md
├─ 00_problem/                 # 题目、官方附件、官方模板
├─ 01_data/
│  ├─ raw/                     # 原始数据副本，不修改
│  ├─ processed/               # 清洗/变换/特征数据
│  └─ external/                # 外部真实数据
├─ 02_analysis/
│  ├─ security_audit/
│  ├─ problem_analysis.md
│  ├─ assumptions.md
│  ├─ symbols.md
│  ├─ model_plan.md
│  ├─ PAPER_EVIDENCE_BLUEPRINT.md
│  ├─ BLIND_BENCHMARK_PROVENANCE.md
│  └─ qN_solution.md
├─ 03_code/
│  ├─ common/
│  ├─ q1/
│  ├─ q2/
│  └─ 总运行.py或现有稳定入口
├─ 04_results/
│  ├─ figures/
│  ├─ tables/
│  ├─ data/
│  ├─ logs/
│  └─ VISUALIZATION_MANIFEST.md
├─ 05_paper/
├─ 06_submission/
├─ 07_references/
└─ 99_temp/
```

不提前创建没有实际用途的空目录。只为实际开展的问题创建 `qN/`，不预建尚未开展的后问目录。

已有仓库、CI、包模块、Notebook 或工具链采用其他合理结构时，映射职责即可，不强制套模板或改成中文文件名。

## 2. 根 README 是接手入口

工作区 `README.md` 只记录队员接手需要的信息：

- 赛题、当前进度和各问状态；
- 文件安全审计状态；
- 运行模式：LIVE_CONTEST / BLIND / OPEN_REFERENCE；
- 协作模式：`agent_mode: SINGLE | THREE_ROLE`；三角色时记录可复用角色、当前任务与共享文件唯一写入者；
- Skill 版本与 commit、模型、推理档位和工具权限（可取得时）；
- 每问主入口和 `FINAL_RUN_ID`；
- 当前主路线、重大风险和待确认事项；
- Evidence Blueprint、关键决策、结果、论文、交付根目录和官方提交候选位置；
- 每问计算、核验、论文材料、交付四项状态及证据/缺口；
- 关键运行命令。

路线、Final Run、入口、协作模式或输出路径变化时同步更新。无法取得精确信息时写 unknown/unavailable，不猜测。模式首次选择和切换按 [核心流程](core-workflow.md)，不要建立另一份与 README 不一致的协作状态表。

## 3. 原题与数据边界

### `00_problem/`

只保存官方原题、附件和模板。原件不被清洗脚本或审计流程覆盖。

### `01_data/raw/`

保存程序实际读取的原始数据副本、解压后的原始表或按 Sheet 导出的原始内容，必须能映射回官方附件，不写入清洗结果。

### `01_data/processed/`

保存清洗、合并、单位统一、零值/缺失处理和特征构造后的数据。每个重要文件能追到来源文件/Sheet/字段、处理脚本、规则、单位变化和使用它的 Run。

### `01_data/external/`

保存从政府、统计机构、对象官网、行业机构或其他可靠来源取得的外部原始数据。记录发布机构、URL、获取日期、时间/空间范围、单位、口径、许可、处理脚本和实际用途。

严禁把假设、插值、估计或仿真冒充观测数据。

## 4. 分析与版本溯源

### `security_audit/`

保存正常人类视图、隐藏对象可见化图、Evidence ID、哈希、OCR 对照和安全报告。安全审计图不属于论文结果图。

### `problem_analysis.md / assumptions.md / symbols.md / model_plan.md`

分别维护题意与跨问关系、假设及风险、符号/单位/代码映射、候选路线与用户确认。

关键建模决策沿用已有 `q{k}_model.md`，不存在时写入 `q{k}_solution.md`，以 `Q{k}-D{nn}` 标识，记录难点、备选、采用/舍弃依据、验证和影响。蓝图与论文引用该权威记录，不另造重叠决策台账。三角色模式下该文件默认由建模手维护；其他角色提交修改建议或经明确交接后接手，不同时改写。

### `BLIND_BENCHMARK_PROVENANCE.md`

旧题盲测记录 Skill/commit、模型、推理档位、工具、搜索边界、题目哈希、冻结时间、冻结产物 hash 和参考资料开放时间。开放参考后的改进另建版本并标记 POST_HOC。

### `PAPER_EVIDENCE_BLUEPRINT.md`

读题后即建立 EARLY_SKELETON，逐问补充；各问 Final/Validation Run 与正式证据齐备后再 FINAL_FREEZE。早期只填原题要求和依赖，不提前索要尚未生成的论文、图表或运行。

## 5. 代码与结果

正式源码进入 `03_code/`，遵循项目现有命名和 `python-code-documentation-policy.md`。新建中文赛题项目可使用 `第一题.py` 等中文语义名；已有工程优先保持既有约定。

建模计算使用团队实际选择的语言和工具，交付相应入口、版本与复现说明，不为统一名称强行迁移。论文图表须有 Python 脚本和正式数据接口；MATLAB/R 等计算结果先导出带单位、字段和版本的可读取数据，再进入 Python 绘图，不靠手抄数值或软件截图制作论文表。

要求：

- 路径相对项目根目录；
- 不硬编码个人绝对路径；
- 不覆盖 raw/官方附件；
- 正式输出统一写入 `04_results/`；
- 临时调试进入 `99_temp/`；
- 关键运行登记 Run Ledger；
- 每问明确 Final Run；
- 旧结果标记或归档，不能与当前最终结果混用。

使用 run_record.py 时，运行专属的 logs/runs/Rxxx/artifacts/ 也属于正式可追溯产物。向 data/tables/figures 导出整理副本时登记源 Run 和 hash；后问引用明确路径，不能凭同名 latest 文件猜版本。

`04_results/figures/` 按 paper / method / validation / exploration / ai_communication 分用途；普通表格进入 `tables/`，不截图冒充可编辑表格。

本问结果就绪即产出必要论文图表并登记来源，不把全部制图积压到最后。三角色的可写路径和输入版本按 [多代理协作](multi-agent-collaboration.md) 约定；`common/`、蓝图、README 和论文合稿等共享文件均指定唯一写入者。

## 6. 论文、交付目录与官方提交

`05_paper/` 保存论文主线、提纲、逐问协作稿、摘要候选和已确认终稿。论文从读题起介入、随问积累，保持来源和完成状态清楚；队员已有摘要与正文的有效表达优先保留，不无条件要求重新写一遍。未经核查的协作稿不能冒充终稿，AI 使用与披露按当年规则处理。

完整项目首次形成成果时准备交付目录，在 README 明确 `delivery_root`。用户指定路径或已有交付目录优先；否则使用项目根下独立的 `交付文件夹/`。它可以位于工作区外，但不与原始数据、代码工作目录或运行目录共用。目录职责示例：

```text
交付文件夹/
├─ 交付说明.md            # 先看什么、当前范围、如何复现、仍缺什么
├─ 交付清单.json          # files[{path, sha256, size}]，不包含清单自身 hash
├─ 论文/                  # 当前有效源稿、PDF与所需素材，按实际格式
└─ 支撑材料/
   ├─ 01_结果表/
   ├─ 02_求解代码与输入/  # 含环境、依赖及运行入口
   ├─ 03_补充实验/
   ├─ 04_验证记录/        # 含必要推导、决策和结论边界
   └─ 05_论文图表/
```

只建立本次实际需要的目录；既有合理结构沿用，不复制样例的双层同名“支撑材料/支撑材料”，不把示例软件品牌当必需组件。交付目录是有效成果的可携带副本，不是运行缓存，也不是另一套手工维护的计算来源。

成果变化时即按 [动态交付规则](final-delivery-packaging.md) 核验并同步支撑材料、交付说明与清单，每问完成后再整体核对。清单记录源路径、Run/方法版本及 hash；文件、图表、正文应来自同一有效版本。生成新结果后旧交付副本若尚未同步，明确标过期/待同步，不能仍显示为当前完成。队员修改过的摘要、正文或交付文件先识别并保留，未经对账不自动覆盖。无关旧 Run、调试缓存和内部代理任务单留在工作区；必要 AI 披露、引用与许可说明按实际规则保留。

`06_submission/` 保存按当年规则核验的官方提交候选、检查单及按需内部导出。题目详解、参考论文、源码、其他四包是可选导出，可沿用 `06_submission/internal_delivery/`；不得把“存在四包”作为交付目录可用或终稿导出的前提。

真正上传文件以当年官方、赛区和系统规则为准。交付目录验收与官方提交验收分开；不把整个工作区或交付目录原样压缩后就声称可上传。具体选编与验收见 [交付规范](final-delivery-packaging.md) 和 [官方提交规范](official-submission-policy.md)。

---

## 7. 临时文件与清理

`99_temp/` 可存放临时下载、解包缓存、转换文件、一次性脚本和预览图。

最终代码、数据、证据、图表和报告不能只存在临时目录。清理前确认没有正式成果依赖其中内容。

---

## 8. 每问/全题检查

- [ ] 根目录没有散落唯一正式脚本、CSV 或图片；
- [ ] 原题、官方附件和 raw 数据未被覆盖；
- [ ] raw / processed / external 分层清楚；
- [ ] 外部数据有来源和口径；
- [ ] 本问代码入口、Final Run 和结果路径可定位；
- [ ] 图、表、数值和日志进入 `04_results/`；
- [ ] 盲测版本和参考资料开放边界已记录（适用时）；
- [ ] Evidence Blueprint 与逐问论文材料同步积累，完整稿定稿前完成证据冻结；
- [ ] 草稿、队员终稿、内部包和官方候选没有混淆；
- [ ] 当前问所需论文图表已由 Python 生成，或明确未完成/无需作图及理由；
- [ ] 交付目录可直接定位本次有效成果，版本与来源一致；未生成四包不影响此项；
- [ ] 三角色模式下共享文件仅一个写入者，模式和接手信息与实际执行一致；
- [ ] 用户原文件未被擅自破坏；
- [ ] 根 README 与实际目录一致。
