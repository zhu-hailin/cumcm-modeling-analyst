# 两阶段赛题工作流

## 目标

避免 AI 在没有充分理解题目、数据和方法适配性的情况下直接开始长篇求解。先形成可审查的路线决策，再沿确认后的路线一次性解决整题；第二阶段完成后继续完成代码实现、运行验证、教学材料和最终四包交付。

## 第一阶段：赛题预分析与路线决策

### 必须完成

1. 题目背景：现实场景、研究对象、为什么值得建模；
2. 题面事实：明确要求、输出、约束、单位、时间和空间范围；
3. 子问题拆解：每问核心任务、输入、输出、前置依赖和验收标准；
4. 逐问核心思路：按题面实际子问题数量依次说明每一问的本质任务、关键变量与约束、前后依赖和分析链；
5. 逐问解法评分：每一问在核心思路之后列出通常 2–3 条有实质差异的候选解法，给出具体算法/模型，并按统一 100 分制评分、排序、解释和推荐；若不存在有意义的第三条方案，不得为了凑数制造伪候选；
6. 逐问结论：明确每一问的首选解法、备用解法和切换条件；完成当前问题后再进入下一问；
7. 各问推荐总览：用一张表快速汇总每问的核心思路、首选算法、推荐指数和备用方案；
8. 整体候选路线：在逐问分析完成后，再形成至少三条实质不同的整题路线；
9. 主路线：说明为什么整体上最协调，而不是每问各选一个孤立模型；
10. 首轮文献与数据证据：AI 主动检索、核验并说明每项资料对哪一问有何帮助；
11. 证据缺口：仅在确实无法核验或资料不足时列出缺口、影响和建议检索式；
12. 风险：哪些因素可能迫使换路线；
13. 待确认项：AI 完成上述分析与推荐后，再请用户确认关键路线决定。

### 默认展示顺序

对每一个实际子问题重复以下结构：

`核心思路 → 候选解法 100 分制评分与排序 → 本问首选/备用/切换条件 → 下一问`

全部子问题完成后再进入：

`各问推荐总览 → 整体候选路线 → 主路线推荐 → 文献与数据证据 → 待确认项`

题目常见为三问，但工作流不得把子问题数量固定为三问；必须以题面实际结构为准。

### 用户确认的时机

正常情况下，不得在逐问核心思路与候选方案评分完成之前，先要求用户替 AI 选择模型或从抽象算法名中做决定。AI 应先承担首轮方案筛选责任并给出推荐，再在第一阶段末尾进入 `WAITING_FOR_CONFIRMATION`。

只有缺失信息足以改变题意、核心约束、数据可用性或路线可行性时，才允许提前询问阻塞性信息。轻微缺失应明确假设后继续分析。

### 第一阶段代码边界

第一阶段只做路线决策，不生成最终可执行代码。可以给出实现复杂度、模块需求和算法步骤，但不要在路线尚未确认时投入完整代码实现。

### 禁止事项

- 不直接写整题完整推导；
- 不给虚构的数值结果；
- 不假装已读取不存在的附件；
- 不在未经确认时把某条候选路线写成唯一正确答案；
- 不因为某算法看起来高级就提高推荐指数；
- 不在解释本问核心思路之前先堆模型名称；
- 不用多个几乎相同的算法变体伪装成不同候选方案；
- 不把本应由 AI 完成的首轮方法比较提前转交给用户；
- 不在第一阶段提前生成最终源码。

### 第一阶段结束状态

输出 `WAITING_FOR_CONFIRMATION`，等待用户确认、调整或继续补充论文。

## 持续文献更新机制

AI 应在第一阶段主动完成首轮文献和数据来源检索。团队后续提供的论文属于持续补充证据，可以在任何阶段进入，不局限于第一阶段与第二阶段之间。

每篇由 AI 检索到或由团队补充的新论文都要回答：

- 是否补充题目背景；
- 是否支持变量或指标；
- 是否提供模型、参数、数据或验证方法；
- 是否与当前题目规模和假设匹配；
- 是否改变某问算法或整体主路线；
- 是否调整路线推荐指数；
- 是否值得进入正式参考文献。

若证据不足，只标记待核验，不得用来锁定路线。若当前环境不能联网或读取全文，应明确说明能力边界，并提供可执行的检索式；不得虚构结果，也不得把首轮检索默认外包。

## 路线确认

路线确认时记录：

- 各问最终方法；
- 整体问题链；
- 关键变量和约束；
- 已采纳论文；
- 暂定参数；
- 验证方法；
- 备用路线与切换条件；
- 明确不采用的方案及原因。

确认后进入 `STAGE_2_LOCKED`。

## 第二阶段：一次性完整求解与实现

### 求解顺序

按依赖关系求解，而不是机械按题号：

`数据准备 → 公共变量与假设 → 前置问题 → 后续问题 → 全局验证 → Python 实现 → 运行产物 → 教学材料 → 最终打包`

### 每问完整结构

1. 该问目标；
2. 前一问传入的结果；
3. 输入、输出和符号；
4. 假设；
5. 模型定义；
6. 目标函数或核心关系；
7. 约束；
8. 参数来源；
9. 算法步骤；
10. Python 实现映射；
11. 实际结果和图表；
12. 验证；
13. 向下一问传递什么。

### 第二阶段代码实现

路线确认后，代码实现成为第二阶段正式交付的一部分：

- 为最终采用方案生成完整 Python 代码；
- 按实际赛题编号和问题编号组织；
- 公共模块单独放置，避免重复；
- 当前环境允许执行 Python 时，实际运行关键入口并修复明显错误；
- 保存 Python 生成的关键图片、表格和必要中间结果；
- 记录依赖、运行顺序、参数和随机种子；
- 教程中的代码路径、函数和输出必须与最终源码一致。

不得用伪代码代替最终源码，也不得为了“代码很多”而制造无用文件。

### 路线锁定规则

- 不得为了写起来方便而临时换模型；
- 小调整需要注明；
- 若新证据只是改善参数、变量或验证，保持路线不变；
- 若新证据推翻核心假设或使模型不可行，输出 `ROUTE_REOPEN_REQUIRED`；
- 重新开路线必须比较旧路线和新路线的分数与代价。

## 最终交付阶段

完成第二阶段建模、代码、运行验证、教程和文献整理后，读取 [final-delivery-packaging.md](final-delivery-packaging.md)，进入最终打包。

最终只应优先交付四个 ZIP：

```text
题目详解.zip
参考论文.zip
源码.zip
其他.zip
```

### 题目详解.zip

按实际子问题逐问生成教程，教程必须结合最终源码教会队员，包括模型推导、代码映射、运行方式、输出解释、验证、常见错误和论文表达。

### 参考论文.zip

只允许放真实论文原文件 `.pdf`、`.doc`、`.docx`。无法取得原文件但值得记录的资料放到 `其他.zip` 的文献来源记录中，不得伪造论文文件。

### 源码.zip

放置全部最终 Python 代码、必要依赖、数据以及 Python 生成的图片、表格和中间结果，并按实际赛题编号和问题编号组织。

### 其他.zip

放置 AI 使用说明、人工复核、建模决策、路线变更、文献账本、数据来源、环境说明和其他必要文件。

四包通过打包自检后，阶段状态记为 `FINAL_DELIVERY`。

## 同一回复内完成两阶段

仅当用户明确要求“先给推荐，再在同一份输出中完整解决”时：

1. 先完整输出第一阶段；
2. 插入明显分隔线；
3. 写明“以下基于暂定主路线直接进入第二阶段”；
4. 再输出完整求解和代码实现；
5. 对未获用户确认的关键决策标记为“暂定”；
6. 若同时要求最终交付，则继续按最终四包规范打包。
